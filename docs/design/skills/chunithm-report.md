# 유니 스킬: chunithm-report

Oct 9, 2026 · @astrove

동기화된 기록을 조회하고 분석하는 스킬이다. 동기화 리포트의 본문(세션 요약과 갱신 목록)도 이 스킬이 조각으로 만든다. 동기화 리포트의 지표는 현재값과 직전 동기화 대비 변화량을 함께 보여 준다(세션 맥락이라 변화량이 의미 있다). 프로필·베스트 같은 단순 조회는 지금 값만 보여 준다(사용자 확인 2026-10-18 — 변화량은 세션 맥락에서만 의미 있다). 숫자는 모두 `records` 서비스가 계산한다.

## 개요

```yaml
name: chunithm-report
description: 내 레이팅, 베스트 30과 신곡 20, 최근 플레이, 곡별 기록을 보여 주고 레이팅을 올릴 후보곡을 분석한다. 공개한 다른 플레이어의 기록도 볼 수 있다.
examples:
  - 내 베스트 30 보여 줘
  - 레이팅 올릴 곡 추천해 줘
  - 민수 크로노 기록 몇 점이야?
category: 기록과 리포트
game: chunithm
version: 1
services: [records, songdb, players, chunithm_net]
tags: [chunithm-synced]
listens: [chunithm.sync.completed]
```

`recent`는 저장된 데이터가 없어(기록 테이블에는 PB·세션·동기화 로그만 있다) 그 자리에서 `chunithm_net`으로 최근 플레이를 가져오므로 `chunithm_net`이 services에 들어간다.

다른 플레이어의 기록을 보는 것도 요청한 사람에게 `chunithm-synced`가 있어야 한다. 이것이 너무 엄격하면 남의 기록 조회 도구만 태그 없이 둔다(아래 미확인 사항).

## 레이팅 계산 (`records` 서비스가 하는 일)

- 전체 레이팅은 베스트 30곡과 신곡 20곡의 곡 레이팅 합을 50으로 나눈 값이다. 신곡 여부는 Chunimaru songdb의 신곡 기준일로 판정한다.
- 곡 레이팅은 상수에 점수 구간별 가산을 더한다. 구간 사이는 직선으로 잇는다.
- 곡 레이팅은 소수 둘째 자리에서 버린다(실제로 더 가는 단위가 없다 — 점수 구간 가산 공식 자체가 1점당 변화량이 0.01 단위라, 둘째 자리보다 더 쓴다고 더 정확해지지 않는다. 4단계에서 저장본으로 검산해 확인했다: 곡마다 둘째 자리에서 버린 뒤 합산해야 CHUNITHM-NET 표시 레이팅과 맞고, 채보별 레이팅 자체를 넷째 자리까지 들고 있다가 마지막에만 버리면 어긋난다). 베스트30 평균·신곡20 평균·**전체 레이팅**(각각 30·20·50으로 나눈 값)은 모두 넷째 자리에서 버린다(`records_calc.average_rating` 기본값, 사용자 확인 2026-10-18). 전체 레이팅(분모 5000=2³×5⁴)과 신곡20 평균(분모 2000=2⁴×5³)은 넷째 자리에서 정확히 끝나고, 베스트30 평균(분모 3000)은 3이 섞여 애초에 안 끝나지만 세 지표를 같은 자리수로 맞춘다. CHUNITHM-NET 표시값은 둘째 자리까지만 보여주므로, 동기화마다의 대조(`rating_mismatch`)는 전체 레이팅을 둘째 자리로 버린 뒤 비교한다.
- 계산한 레이팅이 CHUNITHM-NET 표시값과 맞는지 동기화마다 대조한다.

| 점수 | 곡 레이팅 |
| --- | --- |
| 1,009,000 이상 (SSS+) | 상수 + 2.15 |
| 1,007,500 (SSS) | 상수 + 2.00 |
| 1,005,000 (SS+) | 상수 + 1.50 |
| 1,000,000 (SS) | 상수 + 1.00 |
| 975,000 (S) | 상수 |

이 표와 공식은 구현 전에 게임 버전에 맞는지 다시 확인하고, CHUNITHM-NET 표시값 대조로 검증한다. 975,000점 미만 구간은 이 표에 없으므로 구현 전에 확인해 더한다.

## 조회와 분석

- **프로필**: 닉네임, 현재 레이팅, 베스트 30 평균, 신곡 20 평균(지금 값만, `records.latest_sync_summary`), 마지막 동기화 시각. 변화량은 안 보여준다 — 동기화 리포트 전용이다(사용자 확인 2026-10-18). 베스트 목록의 평균과 레이팅도 같은 값을 쓴다.
- **베스트 목록**: 베스트 30과 신곡 20 각각의 채보, 점수, 곡 레이팅, 전체 레이팅 기여도. 이미지나 표로 낸다.
- **최근 플레이**: CHUNITHM-NET 최근 플레이 이력. 판정 수까지 보여 준다.
- **곡별 기록**: 채보 하나의 내 최고 기록. (판정 수는 7단계에서 뺐다 — PB(베스트30/신곡20/전체 PB)는 판정 수를 저장하지 않는다. 결정 사항 E와 같은 한계로, CHUNITHM-NET이 그 목록 조회에서 판정 수를 주지 않는다.)
- **분석**: 상수대(상수의 정수 부분, 예: 15.3 → 15대)별 평균 점수와 랭크 분포. (판정 수 기반 어택·미스 비중은 7단계에서 뺐다 — PB에는 판정 수가 저장되지 않는다.)
- **후보곡**: 미플레이이거나 점수가 낮은 채보 중 프레임에 들어갈 때 레이팅 상승폭이 큰 순. 기준은 SSS(상수+2.00) 달성이다(사용자 결정 2026-10-17): 상승폭 = (상수+2.00) − (그 채보가 속할 쪽 프레임의 현재 최저 레이팅 — 신곡이면 신곡20, 아니면 베스트30). 안 친 채보는 현재 점수 0으로 보고, 각 후보에 SSS까지 남은 점수를 붙인다(어택은 보더 확인에만 쓴다 — 사용자 확인 2026-10-20).
  **추천 대역(사용자 결정 2026-10-19)**: SSS를 냈을 때 곡 레이팅(상수+2.00)이 그 채보가 속할 쪽 프레임의 3~8위 레이팅 사이(양끝 포함)인 채보만 후보로 한다 — 상수 높은 곡이 수백 어택짜리로 위에 뜨던 것을 막는다. 예: 베스트30의 3위가 17.10, 8위가 17.01이면 SSS 17.10~17.01이 되는 채보만(상수 15.1). 정렬은 그대로 상승폭 내림차순. 프레임이 8곡에 못 미치면 있는 곳까지만 쓰고, 3곡도 없으면 그 프레임 쪽 후보는 없다.
- **다른 플레이어**: `PlayerRef`로 받고, 대상이 기록을 공개한 경우만 보여 준다. 비교는 양쪽 모두 공개한 경우만 한다.

## 동기화 리포트 조각 (order 10)

1. **세션 요약**: 전체 레이팅, 베스트 30 평균, 신곡 20 평균 각각의 현재값과 변화량, 갱신한 채보 수.
2. **갱신 목록**: 채보별 점수 변화, 랭크 변화, 곡 레이팅 변화, 프레임 진입·이탈. ("전체 레이팅에 준 영향"은 7단계에서 뺐다 — records가 채보 하나의 기여분만 따로 계산해 주지 않는다(`records.candidates`의 "기여도"는 조회 전용이고 동기화 경로에는 없다). 필요해지면 records에 그 계산을 추가해야 한다. 전체 레이팅이 2026-10-18부터 넷째 자리까지라 곡 레이팅 변화와 자릿수 자체는 더 이상 안 어긋난다.)
3. **반응 단계와 다음 곡**: `data`에 코드가 고른 반응 단계와 다음에 볼 채보 하나를 넣는다. 유니는 이 단계에 맞는 말만 한다.

| 상황 (코드가 판정) | 반응 단계 |
| --- | --- |
| 개인 최고 갱신, 신규 SSS 이상 | `great` (SSS·SS 계열) |
| 같은 상수대의 평소 점수 수준 | `good` (AAA·AA 계열) |
| 목표에 조금 못 미침 | `close` (BBB·BB 계열) |
| 평소보다 크게 낮음 | `rest` (C·D 계열) |

7단계 구현은 축소판이다: SSS 이상 갱신이 하나라도 있으면 `great`, 그 밖의 갱신이 있으면 `good`, 갱신 없이 플레이만 했으면 `close`, 새 플레이가 없으면(변화 없음) 단계 없이 간단한 조각만 낸다. `rest`와 "평소 점수 수준" 기준은 실제 기록을 보고 다음에 정한다(미확인 사항). 다음에 볼 채보 추천은 지금은 넣지 않고 이후 단계에서 채운다.

다른 조각도 반응 단계를 낼 수 있다. 예를 들어 목표 스킬은 To-Do를 달성하면 `great`를 낸다. `yuni` 서비스는 조각들의 단계 중 가장 높은 것을 쓴다.

형식 예시 (가상의 값)

```text
세션 요약  10/08
레이팅      16.8000 → 16.8100  (+0.0100)
베스트 30   16.9600 → 16.9800  (+0.0200)
신곡 20     16.5700 → 16.5700  (+0.0000)
갱신 2채보

갱신
곡 A MAS 15.3  1,006,800 → 1,007,620  SS+ → SSS  곡 레이팅 17.16 → 17.31
곡 B MAS 14.9  1,008,100 → 1,008,700  SSS 유지   곡 레이팅 16.96 → 17.02
```

- 새 플레이가 없으면 세션 요약과 갱신 목록 없이 "변화 없음"과 함께 레이팅, 베스트 30 평균, 신곡 20 평균을 낸다. 변화 없음이어도 현재값과 변화량을 함께 낸다.
- 여러 날이면 갱신 목록을 날짜별로 나눈다. 세션 요약의 레이팅·평균 숫자는 동기화 전체(직전 동기화 → 지금) 기준으로 한 번만 쓰고 머리줄에 날짜들을 나열한다(날짜별 레이팅은 저장하지 않아 쪼갤 수 없다). 날짜가 추정인 세션과 갱신에는 표시를 붙인다.
- `focus`가 있으면 갱신 목록을 그 채보로 거른다. 세션 요약은 그대로 둔다.

## 데이터

이 스킬의 테이블은 없다. 기록, 스냅샷, 변화량은 `records` 서비스에 있다.

## 유니 지침 (SKILL.md 본문 초안)

- 레이팅과 평균은 지금 값을 말한다. 직전 동기화 대비 변화량은 동기화 리포트에만 나오고, 프로필·베스트 조회에는 안 붙는다.
- 레이팅 하나만 물으면 말로 답하고, 목록과 분석은 표시물로 보여 준다.
- 나쁜 결과나 부족한 점수는 돌려 말하지 않고 숫자 그대로 전한다.
- 다른 플레이어의 기록이 비공개라는 오류가 오면 비공개라고만 말한다. 다른 경로로 찾지 않는다.

## 테스트

- 레이팅 계산이 저장본 CHUNITHM-NET 표시값과 맞는지.
- 구간 사이 점수의 곡 레이팅 직선 보간.
- 후보곡 순서가 레이팅 상승폭순인지.
- 반응 단계 판정 경계값.
- 비공개 플레이어 조회가 함수까지 오지 않는지.

## 미확인 사항

- "평소 점수 수준"과 "크게 낮음"의 기준값. 같은 상수대 평균에서 몇 점 차이로 나눌지 실제 기록을 보고 정한다.
- 자기는 동기화하지 않았지만 남의 공개 기록은 보고 싶은 경우를 허용할지.

## 구현 결정 (2026-10-18, 실기에서 받은 정정)

- 전체 레이팅(computed_rating, 50으로 나눈 값)은 둘째 자리가 아니라 **넷째 자리에서 버린다** — 분모 5000(=2³×5⁴)이라 넷째 자리에서 정확히 끝나서다. CHUNITHM-NET 표시값은 둘째 자리까지만 보여주므로, `rating_mismatch` 대조는 전체 레이팅을 둘째 자리로 버린 뒤 비교한다(`records.save_sync`).
- 베스트30 평균·신곡20 평균도 둘째 자리가 아니라 **넷째 자리에서 버린다**(사용자 확인 2026-10-18 — 세 지표를 같은 자리수로 통일). `records_calc.average_rating`의 기본값을 `places=4`로 바꿨다. 베스트30 평균(분모 3000)은 3이 섞여 넷째 자리에서도 정확히 끝나지는 않지만, 둘째 자리보다는 더 정밀한 값을 보여 준다.
- **프로필·베스트에서 직전 동기화 대비 변화량을 뺐다**(사용자 확인 2026-10-18). 10/17에 세션 리포트용 변화량 스냅샷(`records.rating_deltas`)을 만들면서 "일관성 있게" 프로필·베스트에도 같이 붙였는데(b5ab365), 단순 조회에 변화량이 꼭 필요하다는 근거는 없었다 — 변화량은 세션(동기화) 맥락에서만 의미 있다. `profile`·`best`는 이제 `records.latest_sync_summary`(지금 값만)를 쓰고, `rating_deltas`는 동기화 리포트 조각(`on_sync_completed`)에만 남는다.

# 유니 스킬: chunithm-updates

Oct 9, 2026 · @astrove

국제판과 일본판 공식 공지와 곡 목록을 주기적으로 확인해, 업데이트가 있는 날 서버 채널에 유니가 알리는 스킬이다. 신곡 이름과 레벨은 곡 목록 비교 결과만 쓴다.

## 개요

```yaml
name: chunithm-updates
description: 츄니즘 국제판·일본판 업데이트 일정과 신곡을 알려 주고, 업데이트 알림을 켜고 끈다.
examples:
  - 다음 업데이트 언제야?
  - 이번에 들어온 신곡 보여 줘
category: 알림
game: chunithm
version: 1
services: [songdb, records, notify, http, players, yuni]
emits: [chunithm.update.detected]
listens: [chunithm.sync.completed]
```

태그 조건은 없다. 알림 설정을 바꾸는 도구만 `admin`이 필요하다.

## 확인하는 곳

| 대상 | 확인하는 곳 | 2026-10-08 확인 결과 |
| --- | --- | --- |
| 일본판 공지 | [공식 뉴스 RSS](https://info-chunithm.sega.jp/feed) | 열림. 제목에 업데이트 날짜가 들어 있고, 업데이트 이틀쯤 전에 게시됨 |
| 일본판 곡 목록 | [공식 music.json](https://chunithm.sega.jp/storage/json/music.json) | 열림. 1,759건 (WORLD'S END 포함) |
| 국제판 공지 | [공식 뉴스 페이지](https://info-chunithm.sega.com/) | RSS 없음. "Details of 10/8 Update" 형식의 글이 전날 올라옴 |
| 국제판 곡 목록 | [공식 music.json](https://chunithm.sega.com/assets/data/music.json), Chunimaru songdb | 둘 다 열림. 공식 1,489건, Chunimaru 1,574곡 |

이 표는 조사 시점의 값이다. 구현할 때 다시 열어 확인한다.

## 동작

1. 두세 시간에 한 번 공지를 확인한다(예약 작업, `catch_up`). 새 글이 있으면 제목에서 업데이트 날짜를 뽑아 저장하고, 그날 오전 10시에 도는 알림 예약을 만든다.
2. 업데이트 당일 오전 10시에 지정 채널에 알린다. 공지 링크와 유니 말투의 짧은 요약을 붙인다.
3. 곡 목록의 전후를 비교해 추가된 곡과 삭제된 곡을 코드가 뽑는다. 신곡 이름과 레벨은 이 비교 결과만 쓴다.
4. 국제판 신곡이면 `songdb`에 새로고침을 요청하고 `chunithm.update.detected`를 낸다.

- **일본판 알림**: 서버 설정으로 켜고 끈다. 국제판에 나중에 들어올 곡의 예고로 쓴다.
- **버전업 감지**: 공지 제목의 버전 이름이 바뀌면 따로 크게 알리고, `admin` 태그를 가진 플레이어에게 CHUNITHM-NET 파서 점검이 필요하다고 DM으로 알린다. 버전업 뒤에는 chuni-penguin 어댑터의 수정을 가져와야 할 수 있다.
- **공지를 놓친 경우**: 공지 없이 곡 목록만 바뀌어도 곡 목록 비교로 알린다.
- **개인 멘션 없음**: 업데이트 알림은 채널 공지 한 건이다. 원하는 사람만 받는 역할 멘션을 선택으로 둔다.
- **켜진 직후**: 새벽 정지 뒤 켜지면 공지와 곡 목록을 바로 한 번 확인한다.

**동기화 리포트 조각 (order 40)**

지난 동기화 뒤에 국제판 신곡이 들어왔다면, 그 중 플레이어의 베스트 프레임 상수대에 맞는 채보를 목록으로 돌려준다. 플레이어의 상수대는 `records`에서 읽는다.

## 유니 지침 (SKILL.md 본문 초안)

- 업데이트 날짜와 신곡은 도구 결과로만 말한다. 모르는 날짜는 아직 공지가 없다고 말한다.
- 일본판 소식인지 국제판 소식인지 항상 밝힌다.
- 알림 요약은 두세 문장으로 한다.

## 테스트

- 저장해 둔 RSS와 공지 페이지에서 업데이트 날짜와 버전 이름을 뽑는지.
- 곡 목록 비교의 추가·삭제 계산.
- 같은 공지를 두 번 알리지 않는지.
- 알림 예약이 새벽 정지 시간을 피하는지.

## 구현 결정 (2026-10-18, Part 2 구현)

- **services 보강**: 이 문서 작성(2026-10-09) 뒤에 생긴 예약 인프라(9단계 Part 1)를 쓰므로 manifest에 `settings`·`scheduler`·`db`를 더했다. 실제: `services: [songdb, records, notify, http, players, settings, scheduler, yuni, db]`.
- **`updates_song_snapshots`에 `song_ids_json` 칸 추가**: "추가·삭제 목록"만 저장하면 다음 번 비교의 기준(그때의 전체 곡 id→제목)이 없어진다. 매 확인마다 전체 목록을 같이 저장한다(바뀌었을 때만 새 행).
- **곡 목록 비교는 id 기준**: music.json의 `id`는 안정적인 고유 키다. 제목만 비교하면 리네임을 삭제+추가로 오판한다.
- **버전명 추출은 국제판만**: 국제판 공지의 『버전명』Details of M/D Update" 패턴은 믿을 수 있지만, 일본판 제목은 콜라보 이벤트 이름에도 『』를 쓴다(저장본에 『いよわ』 리바이벌 이벤트가 실례로 있다). 일본판은 `version_name`을 늘 `None`으로 둔다.
- **공지는 오래된 순으로 처리**: 공지 페이지·RSS는 최신 글이 먼저 온다. 버전 비교가 "방금 넣은 값"과 맞대는 방식이라, 최신 순으로 그대로 돌면 켜진 직후처럼 여러 공지를 한 번에 볼 때 옛 글을 나중에 읽어 거꾸로 "버전이 바뀌었다"고 오판한다. `posted_at` 오름차순으로 정렬해 처리한다.
- **"알림 시각"은 서버별 설정이 아니라 고정 10:00**: 이 문서의 설정 표에 "서버" 스코프로 있었지만, 한 번의 `schedule_once`가 모든 서버에 동시에 알리는 구조라 서버마다 다른 시각을 지원하려면 공지당 서버 수만큼 예약을 걸어야 한다. 지인 서버 규모(10명 미만)에서 그 복잡도가 필요 없다고 보고 고정값으로 구현했다. 바꾸려면 먼저 말한다.
- **업데이트 날짜를 못 뽑은 공지는 즉시 알림**: 기다릴 "그날 10시"가 없는 글(버전 자체를 알리는 글 등)은 찾는 즉시 올린다.
- **"공지를 놓친 경우"(곡 목록만 바뀜) 알림은, 같은 확인 주기에 그 지역 공지를 이미 찾았으면 건너뛴다** — 안 그러면 공지 기반 10시 알림과 곡 목록 기반 알림이 같은 사건을 두 번 알린다.
- **새 서비스 메서드**: `RecordsService.new_frame_floor(player_id)`(신곡20 프레임 최저 레이팅, 기존 `_frame_floor` 재사용), `SettingsService.scope_ids_with_value(scope, skill, name)`(그 설정을 켜 둔 길드 전부를 훑는다 — system 플레이어가 길드 하나로 안 좁혀지는 예약 알림이 쓴다).
- **`#채널` 파싱 공통화**: `admin`의 `_parse_channel_id`를 그대로 복사하지 않고 `services/common/notify.py`의 `parse_channel_ref()`로 빼서 두 스킬이 같이 쓴다. `admin/skill.py`도 이걸 쓰도록 바꿨다(동작 동일).
- **동기화 리포트 조각의 "맞는 상수대" 판정**: `candidates()`가 쓰는 것과 같은 식, `candidate_upside(const, new_frame_floor) > 0`(SSS를 냈을 때 신곡20 프레임 최저점을 넘는지)으로 판정한다. 상수를 아직 모르는 신곡(Chunimaru 반영 전)은 조용히 뺀다.

## 미확인 사항

- 국제판 공지 페이지는 RSS가 없어 화면을 파싱한다. 구조가 바뀌면 깨진다. 실패하면 곡 목록 비교만으로 알린다.
- 국제판 공식 곡 목록과 Chunimaru의 건수 차이 원인.

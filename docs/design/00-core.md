# 유니 봇 설계서: 코어

Oct 9, 2026 · @astrove

## 개요

유니 봇은 국제판 츄니즘을 하는 지인 디스코드 서버를 위한 봇이다. 츄니즘의 캐릭터 유니가 서포터로서 플레이어의 기록과 목표를 함께 챙긴다. 처음부터 새로 만들고, 기능은 모두 같은 규격의 스킬 모듈로 꽂는다. CHUNITHM-NET 접속과 파싱만 오픈소스 봇 chuni-penguin의 코드를 가져와 쓴다.

| 항목 | 결정 |
| --- | --- |
| 사용 범위 | 지인 서버, 10명 미만 |
| 대상 게임 | 츄니즘 국제판. 일본판은 업데이트 알림만 |
| 구동 환경 | 우분투 서버 미니 PC(라이젠 5, x86-64), Docker Compose. 매일 새벽 몇 시간 꺼짐 |
| 부르는 방법 | 유니 멘션은 LLM을 거치고, 슬래시 명령은 LLM 없이 같은 기능을 쓴다 |
| LLM | 기본은 Gemini API 유료 등급(에이전트는 Flash, 요약은 Flash-Lite 계열, "비용과 운영" 절). `LLM_PROVIDER` 설정값으로 Claude(Haiku 계열)도 고를 수 있다(6단계 추가, 2026-10-17) |
| 인격 | 유니 단독. 파트너 나비는 이름만 언급하고 화자로 나오지 않는다 |
| 호칭 | 정해 둔 호칭, 없으면 CHUNITHM-NET 닉네임, 그것도 없으면 디스코드 닉네임. 닉네임으로 부를 때는 "상"을 붙인다 |
| 메모리 | LLM이 자동으로 요약해 저장하고, 플레이어가 보고 지울 수 있다 |
| 공개 범위 | 기록은 본인이 공개해야 남이 본다. 메모·목표·오락실·후기는 항목별로 고르고 기본 비공개. 동기화 리포트는 기본 채널 공개 |
| 코드 기반 | 새 저장소. chuni-penguin(0BSD)에서 CHUNITHM-NET 어댑터와 시드 데이터만 가져온다 |

**문서 구성.** 이 문서는 코어, 서비스, 스킬 규격, 인격, 메모리, 운영을 정한다. 기능마다의 세부 동작은 스킬 문서 19개에 있고, 목록과 링크는 "스킬 문서 목록" 절에 있다. 스킬 문서는 이 문서의 규격을 따르고, 둘이 어긋나면 이 문서를 먼저 고친다.

**용어.** 플레이어는 사람 한 명이다. 한 사람이 디스코드 계정을 여러 개 연결해도 플레이어는 하나다. 코어, 서비스, 스킬의 뜻은 "전체 구조" 절에 있다.

## 조사로 확인한 전제

설계의 근거가 되는 사실은 2026-10-08과 10-09에 사이트와 저장소를 직접 열어 확인했다. 모듈 규격은 세 가지 기존 설계를 섞어서 만든다. Claude 스킬에서 단계별 로딩을, MCP에서 도구 정의 형식을, chuni-penguin에서 CHUNITHM-NET 어댑터를 가져온다. 가격과 수치처럼 바뀔 수 있는 것은 구현 때 다시 확인한다.

**Chunimaru** ([API 문서](https://chunimaru.fuwamofu.net/api), [사용법](https://chunimaru.fuwamofu.net/howto))

- 공개 API는 국제판 곡 DB(songdb) 하나뿐이고, 플레이어 데이터 API는 없다. 플레이어 기록은 CHUNITHM-NET을 직접 파싱해야 한다.
- songdb는 1,574곡, 6,399채보를 담고 있고 게임 버전은 X-VERSE-X다. WORLD'S END는 범위 밖이다.
- 제한은 IP당 시간당 30회이고, 데이터는 주에 몇 번만 바뀐다. 문서는 1시간보다 자주 조회하지 말라고 안내한다. ETag 재검증을 지원한다.
- 별칭 필드는 없다. 노트 수가 0으로 비어 있는 채보가 MAS 8개, EXP 16개 있다. 추정 상수 표시가 붙은 채보는 EXP 308개, ADV 12개다.
- 자동 동기화는 암호화한 clal 쿠키만 저장하는 방식이고 국제판에서만 동작한다. 이 봇도 같은 방식을 쓴다.

**공식 출처**: 일본판 공지 RSS와 곡 목록(music.json), 국제판 공지 페이지와 곡 목록(music.json)이 모두 열린다. 국제판 공지에는 RSS가 없다. 자세한 내용은 `chunithm-updates` 문서에 있다.

**chuni-penguin** ([저장소](https://github.com/beer-psi/chuni-penguin))

- CHUNITHM-NET 접속과 파싱은 `chuni_penguin/adapters/`에 분리되어 있다. `NetworkAdapter` 추상 클래스가 프로필, 최근 기록, 베스트, 레이팅 내역, 코스 기록 등을 비동기 함수로 제공한다.
- 실제 구현인 `ChunithmNetAdapter`는 httpx와 selectolax로 HTTP와 파싱을 하지만, `discord.utils.MISSING` 같은 사소한 참조로 discord.py를 가져오긴 한다(우리도 쓰는 라이브러리라 문제는 아니다). 같은 패키지의 `types`, `constants`, `utils`, `calculation`에 의존한다. 점수를 돌려주는 메서드 대부분은 원래 chuni-penguin 자신의 SQLAlchemy DB(곡 메타데이터 보강, 레이팅 계산, PB upsert, 숨김곡 보정)에 묶여 있었는데, 그 보강은 우리의 `songdb`/`records` 서비스가 대신하기로 했으므로 1단계에서 그 결합 부분만 `third_party/patches/`의 작은 패치로 떼어냈다. 또 다른 패치 하나는 전송 계층 문제를 고친다: 원본이 쓰는 `httpx_aiohttp.AIOHTTPTransport`는 그들 저장소 안의 로컬 포크(`packages/httpx-aiohttp`, 버전 `0.1.0`)에만 있고, PyPI에 공개된 `httpx-aiohttp` 패키지는 같은 클래스를 `AiohttpTransport`로 부른다 — 이 차이는 실제로 어댑터를 생성해 보는 테스트가 아니면 안 드러난다(파싱만 테스트해서는 못 잡았다). 두 패치의 상세는 `third_party/patches/README.md`에 있다. 패치 후에는 SQLAlchemy, structlog, chuni-penguin 자신의 설정 파일(`bot.ini`)이 전부 필요 없다. 원본은 Python 3.14 이상을 요구하고, 선택적 네이티브(Rust) 모듈(`penguin-native`)은 음성 기능에만 쓰여 필수가 아니다. 시드 데이터(`database/seeds/songs.json`)는 SQLAlchemy와 무관한 순수 JSON 리스트라 그대로 데이터로 쓸 수 있고, 노트 수, 채보 제작자, sdvx.in 매핑(수록 중인 MAS·ULT 1,672채보 중 1,670개), 곡별 위키 문서명이 들어 있다. 한국어 별칭은 없다.
- 디스코드 기능은 `cogs/` 아래 21개 묶음으로 나뉘고, `cogs/__init__.py`의 `COG_LIST` 한 곳에서 불러온다.
- 라이선스는 BSD Zero Clause(0BSD)다. 복사, 수정, 재배포에 조건이 없다.

**Claude 스킬** ([문서](https://platform.claude.com/docs/en/agents-and-tools/agent-skills/overview))

- 스킬은 `SKILL.md`를 가진 폴더다. 앞쪽 YAML에 `name`(64자 이내)과 `description`(1024자 이내, 무엇을 하고 언제 쓰는지)을 둔다.
- 세 단계로 불러온다. 이름과 설명은 항상 들어가고(스킬당 약 100토큰), 본문은 골랐을 때만 들어가며(5천 토큰 이하), 딸린 파일과 스크립트는 필요할 때만 쓴다.
- 스크립트는 코드가 문맥에 들어가지 않고 실행 결과만 들어간다.

**MCP 도구 규격** ([명세](https://modelcontextprotocol.io/specification/latest/server/tools))

- 도구는 `name`, `title`, `description`, `inputSchema`(JSON Schema), `outputSchema`, `annotations`로 정의한다.
- 입력 오류나 업무 규칙 위반은 `isError: true`인 결과로 돌려주고, 모델이 그걸 보고 고쳐서 다시 부르게 한다.
- 민감한 동작은 사람의 확인을 거치라고 권한다. 여러 묶음을 합칠 때는 도구 이름 충돌을 막기 위해 접두사를 붙이라고 한다.

**Gemini 함수 호출** ([함수 호출](https://ai.google.dev/gemini-api/docs/function-calling), [thinking](https://ai.google.dev/gemini-api/docs/thinking))

- 도구 선택 모드는 auto, any, none, validated 네 가지이고, `allowed_tools`로 이번 호출에서 쓸 수 있는 도구를 좁힐 수 있다.
- 독립된 호출을 한 번에 여러 개(병렬), 앞 결과를 받아 이어서(연쇄) 부를 수 있다.
- 여러 턴에 걸친 호출에서는 모델이 돌려준 thought 블록을 그대로 다시 보내야 추론이 이어진다. 서버가 상태를 들고 있는 방식을 쓰면 서버가 처리한다.
- 도구 정의를 몇 개까지 넣는 게 좋은지는 문서에서 찾지 못했다.

## 전체 구조

봇은 코어, 스킬, 서비스 세 층이다. 멘션은 에이전트를 거치고 슬래시 명령은 바로 도구 실행기로 가지만, 둘 다 같은 스킬 함수에 닿는다.

## 유니 코어

코어는 누가, 어디서, 무엇을 물었는지 정리하고 스킬을 안전하게 실행하는 일만 한다. 츄니즘에 대해서는 아무것도 모른다. 츄니즘을 아는 코드는 모두 서비스와 스킬에 있다.

| 구성 요소 | 하는 일 |
| --- | --- |
| 입구 | 디스코드 이벤트 중 유니 멘션, 스킬이 연 대화 스레드, 유니가 낸 버튼, 슬래시 명령만 받는다. 접두사 명령은 없다. |
| 요청 맥락 | 디스코드 계정을 플레이어로 바꾼다(연결된 계정은 모두 같은 플레이어). 플레이어의 권한 태그, 서버, 채널, 멘션된 다른 사람도 담는다. |
| 에이전트 반복 | LLM 호출, 도구 실행, 결과 전달을 반복한다. 한 요청에 도구 호출 횟수와 토큰에 상한이 있다. |
| 도구 실행기 | 인자를 스키마로 검사하고, 권한 태그와 공개 범위를 확인하고, 확인이 필요한 도구는 버튼을 내고 멈춘다. 오류는 모델이 고칠 수 있게 결과로 돌려준다. |
| 프롬프트 조립 | 규칙 파일, 말투 파일, 플레이어 메모리, 스킬 카드 목록, 펼쳐진 스킬의 지침, 스킬이 내는 프롬프트 조각을 합친다. 카드는 그 플레이어의 태그로 걸러서 넣는다. 규칙 파일이 말투 파일보다 우선한다. |
| 응답 조립 | 유니의 말 뒤에 표시물(임베드, 표)을 고치지 않고 붙인다. `required`는 항상, 작업 표는 턴의 마지막 하나만(유니가 `[[no_table]]`을 쓰면 뺀다), `optional`은 유니가 고른 것만 붙이고, 말 속 숫자를 대조한다. |
| 대화 스레드 | 스킬이 스레드(또는 DM)를 열면 그 안에서는 멘션 없이 듣는다. 무응답 시간이 지나면 끝났는지 묻고, 한 번 더 지나면 닫는다(기본 5분씩, 설정값이고 스킬이 스레드를 열 때 바꿀 수 있다). 닫히면 대화 전문을 연 스킬에 넘기고, 코어는 그 전문을 평소와 같은 메모리 요약 대기 목록에 넣는다. 세션 후기가 첫 사용처다. |
| 권한 태그 | 플레이어가 가진 태그를 모으고, 스킬과 도구의 조건과 맞춰 본다. 자세한 규칙은 "데이터, 권한, 비밀 값" 절에 있다. |
| 메모리 | 플레이어별 기억의 저장, 요약, 프롬프트 주입. 요약에는 싼 모델을 쓴다. 보기·지우기·끄기는 `memory` 스킬이 맡는다. |
| 이벤트 버스와 예약 작업 | 스킬이 내는 사건을 다른 스킬에 전하고, 예약된 작업을 돌린다. 새벽 정지 시간에 놓친 작업을 다시 잡는다. |
| LLM 어댑터 | 모델 제공자를 감춘다. 제공자는 `LLM_PROVIDER` 설정값(부팅 시점에만 고름, 런타임 전환 없음)으로 Gemini/Claude 중 하나를 고른다. Gemini는 공식 SDK google-genai의 비동기 클라이언트(client.aio)로, Claude는 공식 SDK anthropic의 비동기 클라이언트(AsyncAnthropic)로 부른다. 두 SDK 모두 자동 함수 호출은 끄고(Claude는 원래 자동 실행을 안 하므로 해당 없음), 도구 실행은 코어의 도구 실행기만 한다. 모델 이름은 설정값이고, Gemini의 thought 블록 전달 같은 제공자별 처리는 그 어댑터 안에서만 한다(6단계에서 Claude 지원 추가, 2026-10-17). |
| 스킬 레지스트리 | 시작할 때 스킬 폴더와 태그 정의를 읽고 규격을 검사해 등록한다. 규격에 어긋난 스킬은 실패한 이유를 남기고 끈다. |

**코어가 직접 갖는 도구**는 세 개뿐이다. 스킬을 펼치는 `open_skill`, 플레이어 메모리를 남기는 `remember`, 할 수 있는 일을 안내하는 `list_capabilities`다. 여기에 대화 스레드 안에서만 모델에게 보이는 `end_conversation`(대화 끝내기)이 있다. 나머지는 모두 스킬이 가져온다.

**두 갈래 길.** 슬래시 명령은 LLM을 거치지 않고 같은 스킬 함수를 바로 부른다. 멘션은 에이전트 반복을 거친다. 그래서 스킬 하나가 두 길에서 같은 결과를 낸다.

**숫자는 코드가 만든다.** 점수, 상수, 레이팅, 허용 어택 개수는 도구가 계산한다. 유니가 말로 답할 때도 숫자는 이번 요청의 도구 `data`에 있는 값만 쓰고, 서로 빼거나 더해서 새 숫자를 만들지 않는다. 코어는 답을 내보내기 전에 말 속 숫자가 `data`에 있는지 대조하고, 위반이면 로그를 남긴다. (소수점·쉼표 없는 50 이하 정수 — 목록 번호, 베스트 30·신곡 20 같은 프레임 크기, 날짜 — 는 대조에서 뺀다. 2026-10-19 사용자 결정.) 위반 여부와 무관하게 표시물이 붙는 기준은 "표시물 고르기" 절의 `display_mode`·`[[show:<id>]]` 규칙 하나다(실기 2026-10-18 — 위반 시 그 요청의 표시물을 모두 강제로 붙이던 것은 목표 하나만 고쳤는데 조회용으로 부른 다른 도구의 결과까지 새어 나오는 문제가 있어 없앴다, `core/response_assembly.py`). 숫자 규칙을 프롬프트가 아니라 구조로 강제하는 방법이다.

## 스킬 모듈 표준

스킬 하나는 폴더 하나다. 글로 쓰는 부분(소개와 지침)은 `SKILL.md`에, 코드는 `skill.py`에 둔다. 도구 하나를 정의하면 멘션 경로와 슬래시 명령 경로가 함께 생긴다.

### 폴더 구조

```
skills/chunithm-border/

  skill.py        도구, 이벤트 처리, 예약 작업
  models.py       이 스킬 테이블의 행 타입과 SQL 쿼리 (있을 때만)
  migrations/     이 스킬의 SQL 파일, 001_init.sql부터 번호순 (있을 때만)
  reference/      길고 가끔 필요한 참고 자료 (있을 때만)
  tests/          스킬 테스트 (필수)
```

### SKILL.md 본문 (유니에게 주는 지침)

스킬을 펼칠 때만 모델에 들어간다. 어느 도구를 언제 쓰는지, 결과를 어떻게 말해야 하는지, 이 스킬에만 해당하는 규칙을 적는다. 길이는 1,500토큰 안쪽을 목표로 하고, 더 긴 자료는 `reference/`에 두고 읽는 도구를 따로 둔다. 말투는 여기에 쓰지 않는다. 말투는 코어의 말투 파일 하나만 정한다.

### 도구 정의

도구는 타입이 붙은 비동기 함수에 `@tool`을 붙여 만든다. 인자 타입에서 JSON Schema가, docstring에서 설명이 자동으로 나온다. 이름은 `<스킬>_<함수>` 형태로 레지스트리가 붙인다.

| 옵션 | 뜻 |
| --- | --- |
| `slash="보더"` | 같은 함수를 슬래시 명령으로도 연다. 인자는 명령 옵션이 된다. "연결 시작"처럼 띄어 쓰면 하위 명령이 된다(디스코드는 명령·그룹·하위 명령의 세 단계까지). 하위 명령이 있는 명령은 단독으로 쓸 수 없으므로, 같은 이름을 단독 명령과 그룹으로 함께 쓰지 않는다. 슬래시 이름이 겹치면 계약 테스트에서 걸린다. |
| `tags` | 스킬의 `tags`에 더해지는 조건. 스킬은 누구나 쓰되 도구 하나만 제한할 때 쓴다. |
| `mutates` | 데이터를 바꾸는지. 바꾸는 도구는 요청한 플레이어 본인의 데이터만 바꿀 수 있다. 예외는 서버 공유 데이터(별칭, 서버 은어, 오락실 목록, 서버 설정)다. 이런 도구는 바꾼 사람과 시각을 남기고, 남이 만든 것 지우기·승인·서버 설정은 admin 태그를 요구한다. |
| `confirm` | `never`, `bulk`, `always`. `bulk`는 여러 건을 바꾸거나 지울 때만 확인 버튼을 낸다. `bulk` 도구는 `dry_run: bool = False` 키워드를 받는다(스키마에는 안 나온다). 실행기가 먼저 `dry_run=True`로 불러 `data["count"]`를 보고, 2건 이상이면 그 미리보기와 함께 확인 버튼을 내고, 0~1건이면 바로 실행한다. |
| `cost` | `light`, `network`, `llm`. 적지 않으면 light다. CHUNITHM-NET이나 외부 검색을 부르는 도구는 network/llm으로 적는다. |
| `max_calls_per_turn` | 이 도구만 따로 거는 응답당 호출 상한(정수, 기본 없음 — 전역 `MAX_TOOL_CALLS_PER_TURN`보다 좁게 쓴다). 넘기면 그 호출만 에러로 돌아가고 턴은 계속 진행한다(전역 상한은 턴 전체를 멈춘다). |

**표준 인자 타입.** 플레이어, 곡, 오락실을 가리키는 인자는 반드시 아래 타입을 쓴다. 모델은 들은 말을 그대로 넘기고, 코어가 함수를 부르기 전에 실제 대상으로 바꾼다. 바꿀 수 없으면 함수는 불리지 않고 오류가 모델에 돌아간다. 그래서 권한 검사와 곡 이름 해석이 모든 스킬에서 같게 동작하고, 스킬 코드는 이 일을 신경 쓸 필요가 없다.

| 타입 | 모델이 넘기는 것 | 코어가 하는 일 | 함수가 받는 것 | 실패할 때 |
| --- | --- | --- | --- | --- |
| `PlayerRef` | 멘션, 디스코드 ID 숫자, "나"(이름·호칭 매칭은 아직 없다) | `players`로 플레이어를 찾는다. 봇과 상호작용한 적 없는 계정이면 플레이어를 만들지 않는다. 공개 설정은 그 데이터를 읽는 스킬이 검사한다 | 플레이어 | "누구인지 모름" |
| `SongQuery` | 곡 이름, 별칭, 줄임말 | `songdb`의 별칭 검색으로 곡을 하나로 좁힘. 국제판 미수록 곡은 제외 | 곡 | "후보: …"(여러 개) 또는 "찾지 못함" |
| `ChartRef` | `SongQuery` + 난이도 | 위와 같고, 그 난이도 채보가 있는지 확인. 난이도가 없으면 MAS | 채보(상수, 노트 수 포함) | "그 난이도 없음" |
| `ArcadeRef` | 오락실 이름, 별칭, 줄임말 | `arcades`의 이름 확인(정확히 같음, 비슷한 후보, 없음). 별칭은 플레이어별 | 오락실 | "후보: …" 또는 "없음". 새 별칭과 새 오락실은 버튼으로 확정한 뒤에만 저장 |
| `RankRef` | "SSS+", "트플플" 같은 랭크 표현 | `terms`의 별칭으로 정식 랭크로 바꿈 | 랭크와 기준 점수 | "후보: …" 또는 "모르는 랭크" |
| `DifficultyRef` | "MAS", "마스" 같은 난이도 표현 | 같음 | 난이도 | "모르는 난이도" |
| `LampRef` | "풀콤", "올저", "이론치" 같은 램프 표현 | 같음 | 램프(값이 있으면 기준 점수 포함) | "모르는 램프" |
| `ScoreRef` | "1007.5k", "100만 7천5백", "1,007,500" 또는 랭크·램프 이름 | 점수 표현을 읽거나, 랭크·램프를 기준 점수로 바꿈 | 점수(0\~1,010,000) | "읽을 수 없는 점수" |

값이 되는 용어(랭크, 난이도, 램프, 점수)는 모델이 기억으로 해석하지 않는다. 별칭은 `terms` 서비스의 `terms.yaml` 하나에 있고, 그래서 모든 스킬이 같은 은어를 알아듣는다.

후보가 여러 개일 때 멘션 경로에서는 모델이 되묻거나 다시 고르고, 슬래시 경로에서는 코어가 후보 버튼을 낸다. 곡·채보 데이터 자체는 `songdb` 서비스에 있고, `chunithm-song` 스킬은 사용자가 곡 정보를 물을 때 쓰는 창구일 뿐이다. 다른 스킬은 이 스킬을 거치지 않는다.

**도구가 돌려주는 것**은 세 칸이다.

| 칸 | 받는 쪽 | 내용 |
| --- | --- | --- |
| `data` | 모델 | 짧은 JSON. 유니가 말을 만들 때 쓰는 사실과 숫자. 유니가 말할 만한 숫자는 계산까지 끝낸 값으로 넣는다. 예: 남은 어택 개수를 유니가 빼서 구하지 않게 한다. |
| `display` | 사용자 | 임베드나 표. 붙일 때는 코어가 고치지 않는다. 붙일지는 `display_mode`가 정한다. |
| `display_mode` | 코어 | `required`면 항상 붙인다. `optional`이면 유니가 붙이기로 고를 때만 붙인다. 기본은 `required`. |
| `error` | 모델 | 무엇이 잘못됐고 어떻게 고치는지. 예: "곡을 찾지 못함. 후보: …" |

**표시물 고르기**

- 리포트, 목록, 여러 줄짜리 표처럼 말로 옮기면 빠지는 게 생기는 결과는 `required`로 둔다. 보더 하나, 상수 하나처럼 한두 값으로 끝나는 결과는 `optional`로 둔다.
- 모델에는 `optional` 표시물마다 id를 준다. 유니가 답에 `[[show:<id>]]`를 넣으면 코어가 그 표시를 지우고 표시물을 붙인다. 도구를 한 번 더 부르지 않아도 된다.
- 슬래시 경로에서는 `display_mode`와 상관없이 표시물을 항상 보여 준다. 유니의 말이 없기 때문이다.
- **표 빼기(2026-10-19 사용자 결정, 2026-10-20 16단계 Part 4-5에서 정리)**: 유니가 답에 `[[no_table]]`을 넣으면 그 요청의 작업 표를 글자로 붙이지 않는다. 질문이 개수나 한 줄 답일 때 표가 군더더기로 붙는 것을 막는다. 처음에는 목록 도구의 표시물마다 `Display.omittable`을 켜서 이걸 구현했는데, 모든 목록 도구가 작업 표를 돌려주게 되면서 `omittable`과 같은 도구의 `omittable` 표시물을 하나만 남기던 에이전트 코드를 지웠다(작업 표는 턴의 마지막 하나만 붙는다). 출처처럼 도구가 직접 내는 required 표시물은 `[[no_table]]`과 무관하게 항상 붙는다. 걸러 낸 말 속 숫자는 기존 숫자 규칙이 대조하고, 빠뜨림은 못 잡는다.
- **슬래시 전용 본문**: `Display.slash_content`가 있으면 슬래시는 `content` 대신 그것을 보낸다. 멘션은 `content`만 쓴다. 다음 슬래시 명령에 타이핑할 id(`/목표 목록`의 목표 id 등)는 여기에만 넣어 멘션 답에는 안 보이게 한다.
- 언제 붙이고 언제 말로 끝낼지는 스킬의 `SKILL.md` 본문에 적는다. 예시는 아래 보더 스킬에 있다.

### 작업 표 (초안 2026-10-20, 코어 구현 2026-10-20, 스킬 연결은 16단계 Part 2~6 진행 중(Part 4까지 완료), 그림 표 구현 2026-10-20 — `docs/design/skills/chunithm-image.md`)

**왜.** "15 상수 마스 중 SSS 못 한 거"처럼 여러 채보를 고른 뒤 다른 스킬이 채보마다 값을 붙이는 질문은, 지금 구조에서는 모델이 목록을 받아 채보마다 다른 도구를 다시 불러야 한다. 호출 상한(5)에 바로 걸리고, 도구마다 표시물이 붙어 같은 목록이 여러 번 나오며, 숫자가 모델 손을 거쳐 옮겨진다. 그래서 행 목록은 **작업 표**로 만들어 코어가 보관하고, 모델과 스킬은 표 id만 주고받는다.

**표준 입출력 (2026-10-20 결정).** 채보 목록만이 아니라 목표·메모·세션·약속처럼 **여러 항목을 돌려주는 도구의 결과는 모두 작업 표**다. 목적은 모델이 원자료(점수 같은 숫자, 목표 id 같은 내부 값)를 옮겨 적지 않게 하는 것이다. 모델이 받는 것은 표 요약뿐이고, 행 값은 `table_peek`으로 꼭 필요할 때만 본다. 항목 하나를 자세히 보는 도구(`profile`, `chart`, `info`, `record`, `progress`)는 지금처럼 `data`와 `display`를 쓴다. 어느 도구를 바꾸고 어느 도구를 그대로 두는지는 `docs/plan/2026-10-20_수정.md` §16에 도구마다 적었다. 표를 받아 **데이터를 바꾸는** 도구(표로 삭제·완료 등)를 만들지와 그 규칙은 아직 토론 중이다(아래 "결정 대기").

**모양.** 작업 표는 코어가 아는 일반 구조다. 코어는 행이 무엇인지 모른다.

| 부분 | 내용 |
| --- | --- |
| `id` | `t1`, `t2`… 플레이어+채널마다 늘어나는 번호 |
| 가리키는 것 (`ref`) | **행마다 정확히 하나.** 그 행 자체가 무엇인지를 종류와 키로 적는다(예: 목표 행은 종류 `chunithm-goals.goal`, 키 목표 id). 종류 이름은 그 종류를 해석하는 스킬 이름을 앞에 붙이고, 여러 스킬이 같이 쓰는 종류(`chunithm.chart`, `chunithm.song`)만 `services/chunithm`에 정한다. 키는 코어가 보관만 하고 모델에게 보이지 않는다. 스킬 고유 종류는 그 스킬의 도구만 해석한다. 그 행이 채보와 관련 있는지는 이 칸이 아니라 아래 곡·난이도 칸으로 판단한다 |
| `subject` | 표의 데이터가 누구 것인지(플레이어). 키처럼 모델에게 보이지 않는다. 남의 공개 기록으로 만든 표인지 확인하거나, 그림 표가 그 플레이어의 레벨·캐릭터 그림을 찾을 때 쓴다. 플레이어와 무관한 표(곡 검색 등)는 비어 있다 |
| `columns` | 칸마다 이름, 보이는 이름, 값 종류. 값 종류는 `text`·`number` 또는 표준 인자 타입(`ScoreRef`·`RankRef`·`LampRef`·`DifficultyRef`)이다. 칸은 표마다 다르다 — 정해진 칸 목록은 없고, 원천 도구가 처음 칸을 정하고 표를 받는 도구가 칸을 더해 새 표를 낸다. 여러 스킬이 알아봐야 하는 칸은 이름을 한 곳에 정해 둔다(아래 "곡·난이도 칸") |
| 셀 | 셀마다 **원래 값**(거르기·정렬용)과 **보일 글자**(출력용)를 함께 둔다. 보일 글자는 칸을 붙인 스킬이 만든다 — 레이팅 소수 둘째 자리 버림 같은 게임 규칙을 코어가 몰라도 된다. 값이 없을 때의 글자("점수 없음" 등)도 스킬이 정한다 |
| `groups` | 묶음 목록. 묶음마다 **표지**(이름, 행 수, 있으면 묶음 요약)와 그 안의 행(가리키는 것 + 셀)을 가진다. 묶지 않은 표는 이름 없는 묶음 하나다. 행 수는 코어가 센다. 표지에 붙는 개수 단위("15채보", "3개")는 원천 도구가 표에 적어 둔다(`unit`) |
| `summary` | 표 전체 요약값(예: 닉네임, 레이팅). 묶음 요약과 함께 **원래 행 전체에서만 맞는 값**이라 거르거나 다시 묶은 표에는 넘기지 않는다 |
| `steps` | 이 표가 만들어진 과정("15.0 상수 MAS → 내 점수 → 점수<SSS"). 모델과 출력 머리말이 쓴다 |

**묶음·표지·정렬·머리말은 표가 가진다 (2026-10-20 결정).** 보여 주는 구조를 정하는 곳은 표 하나다. 글자 출력과 그림 표는 그 구조를 받아 그리기만 한다.
- 원천 도구가 처음 묶음과 표지를 만든다. `best`는 "베스트 30 · 평균 …"과 "신곡 20 · 평균 …" 두 표지로 만들고, `find_songs`는 묶지 않은 한 묶음으로 만든다.
- 다시 묶기는 `table_query`의 `group_by`가 한다. 그 칸 값마다 묶음이 생기고, 표지 이름은 그 칸의 보일 글자다("15.5" → 출력은 "15.5 · 15채보"). 묶음 요약은 원천 도구만 만들 수 있으니 비운다. `group_by=""`면 묶음을 풀어 한 묶음으로 만든다.
- 묶음 순서: 다시 묶은 묶음은 묶은 칸의 원래 값 내림차순(15.8 → 15.0)이다. 원천 도구가 만든 묶음은 만든 순서(베스트 → 신곡)를 따른다.
- 정렬은 묶음 안에서 한다.
- 거르면 표지 이름은 남고 묶음 요약은 버린다. 비어 버린 묶음은 뺀다.

**표는 바꾸지 않는다.** 칸을 붙이거나 거르거나 다시 묶으면 언제나 새 id의 새 표가 나온다. 원래 표는 그대로 남는다.

**곡·난이도 칸 (2026-10-20 결정).**
- 행이 채보나 곡과 관련 있는지는 **곡 칸과 난이도 칸**으로 판단한다. 표의 종류(검색 결과·목표·메모 등)와 상관없다. 그래서 새 목록 도구도 이 두 칸만 넣으면 `add_scores`·그림 표 같은 채보 도구가 바로 받는다.
- 곡 칸이 차 있고 난이도 칸도 차 있으면 **채보 행**, 곡 칸만 차 있고 난이도 칸이 비어 있으면 **곡 단위 행**(난이도 None), 곡 칸이 비어 있으면 곡과 관련 없는 행이다(예: 레이팅 목표).
- 곡 칸의 **원래 값은 반드시 `songdb`의 정식 곡 제목**이다. 별칭이나 줄인 이름을 넣지 않는다. 보일 글자만 줄여 쓸 수 있다. 우리 곡 데이터에 없는 곡(일본판 신곡, 삭제된 곡 등)은 곡 칸을 비우고 이름을 다른 칸(예: "곡 이름(원문)")에 넣는다.
- 난이도 칸의 원래 값은 `BAS`·`ADV`·`EXP`·`MAS`·`ULT`·`WE` 중 하나이거나 비어 있다.
- 이 두 칸의 이름과 다른 공통 칸 이름(상수·노트 수·레벨·버전·작곡가·점수·랭크·램프·곡 레이팅)은 `services/chunithm`의 한 모듈에 상수로 정하고, 표를 만드는 스킬과 받는 스킬이 모두 그 상수를 쓴다.
- 목표 행의 유형(레이팅·오버파워·폴더·곡·자유)은 가리키는 것에 넣지 않고 **유형 칸**으로 둔다. 목표 DB의 `kind`를 그대로 꺼낸다. "곡 목표만"은 이 칸으로 거른다.

**도구와 표.**
- 여러 항목을 돌려주는 도구는 `ToolResult.table`에 표를 담고 `display`는 비운다.
- 표를 받는 도구는 새 표준 인자 타입 `TableRef`를 쓴다. 모델은 `"t3"`를 넘기고, 코어가 보관소에서 표를 찾아 넘긴다. 이때 소유자(요청한 플레이어)와 채널이 같은지, 아직 살아 있는지 확인한다. 실패하면 "그 표 없음". 다른 플레이어의 기록을 붙이는 도구는 지금처럼 그 스킬이 공개 여부를 검사한다.
- 표를 받는 도구는 **필요한 것**을 선언한다. 선언할 수 있는 것은 두 가지다: 가리키는 것의 종류(예: 목표 도구는 `chunithm-goals.goal`), 또는 차 있어야 하는 칸(예: `add_scores`는 곡·난이도). 코어가 도구를 부르기 전에 행마다 확인한다.
- **필요한 것이 없는 행은 뺀다 (2026-10-20 결정).** 예: 목표 표(레이팅 목표 1개 + 곡 목표 2개)를 `add_scores`에 넘기면 곡이 없는 레이팅 목표는 빠지고, 결과 표에는 곡 목표 2개만 점수 칸과 함께 남는다. 뺀 행 수는 결과 표의 `steps`에 "채보 없는 행 1개 뺌"처럼 적어 모델과 사용자가 알 수 있게 한다. 남는 행이 0개면 도구를 부르지 않고 "대상 행이 없다" 에러를 돌려준다.
- **곡 단위 행을 채보로 펼치기 (2026-10-20 결정).** 곡 단위 행(난이도 빈 값)이 채보가 필요한 도구(점수·보더·채보 링크·폴더 저장·상수대 통계)에 오면 위 규칙대로 빠진다. 그때 뺀 이유를 따로 적는다: steps와 (모두 빠졌을 때의) 에러에 "곡 단위 행(난이도 없음) N개 뺌 — `charts_of`로 난이도를 정할 수 있다". 모델은 이걸 보고 다음 수를 안다.
  - 펼치는 도구는 `chunithm-song.charts_of(table, difficulty: DifficultyRef | None = None)`다. **곡 단위 행만** 그 곡의 채보 행으로 바꾸고, 이미 채보인 행은 그대로 둔다(곡 전체 메모와 채보 메모가 섞인 메모 표에서도 안전하다).
  - 난이도를 주면 그 난이도, **안 주면 MAS**다(사용자 결정 — 모든 난이도로 펼치지 않는다). 그 난이도가 없는 곡은 빠지고 steps에 "ULT 없는 곡 3개 뺌"처럼 적는다.
  - 처음부터 난이도를 말했으면 펼칠 필요가 없다: "nora2r 마스 곡 내 점수" → `find_by_artist(nora2r, difficulty=MAS)` → `add_scores`. 곡 표를 본 뒤 "마스로 점수 붙여줘" → `charts_of("t3")` → `add_scores`.
  - `find_by_artist`가 난이도를 안 받으면 MAS가 아니라 곡 단위 행을 만드는 것(위 "첫 범위")과 다르다. 검색은 곡을 보여 주는 것이 목적이고, 펼치기는 채보 도구에 넘기려는 것이 목적이라서다.
- 표를 돌려받으면 코어가 id를 붙여 보관하고, 모델에는 **표 요약만** 준다: `{table, rows(행 수), columns(보이는 이름), groups(표지 이름과 채보 수), steps, summary}`. 행 내용은 주지 않는다.
- 행 안을 봐야 하면 모델이 코어 내장 `table_peek`을 부른다.

**코어 내장 도구 둘.** 같은 거르기·정렬 엔진을 쓰고, 결과를 어디로 보내는지만 다르다.

| 도구 | 인자 | 결과 |
| --- | --- | --- |
| `table_query` | `table`, `rows`, `exclude_rows`, `where`(조건 목록: 칸·비교·값), `sort`(칸), `descending`, `limit`, `group_by` | 새 표(출력 대상이 된다). 요약은 버리고 `steps`에 조건을 덧붙인다 |
| `table_peek` | `table`, `rows`, `where`, `sort`, `descending`, `limit`(상한 있음) | 고른 행의 원래 값을 모델의 `data`로 준다. 새 표를 만들지 않고 아무것도 출력하지 않는다 |

- `limit`은 **묶음마다** 앞에서 N개를 남긴다("상수마다 점수 높은 3개"). 묶지 않은 표에서는 전체에서 N개다.

**번호로 행 고르기 (2026-10-20 결정).** 사람은 표를 보고 "2번이랑 3번 지워줘", "1번 빼고", "3번 점수 얼마야?"라고 말한다. 모델이 행 값을 읽어 조건을 만들지 않고, 사람이 말한 번호를 그대로 넘긴다.
- `rows=[2, 3]`은 그 번호의 행만, `exclude_rows=[1]`은 그 번호의 행을 뺀 나머지를 고른다. "3번부터 7번까지"는 모델이 `[3,4,5,6,7]`로 펼쳐 넘긴다(범위 문법은 두지 않는다). 다른 조건(`where` 등)보다 먼저 적용한다.
- 번호는 출력할 때 표 전체에 1부터 이어 매긴 번호다(묶음이 있어도 이어진다). 표는 바꾸지 않으므로 한 표의 번호는 언제나 같은 행이다. 글자 출력, 텍스트 파일, 그림 표가 모두 같은 번호를 찍는다. "15.5 묶음의 2번" 같은 묶음 안 번호는 받지 않는다.
- **사람이 본 표에만 쓴다.** 중간 표는 턴이 끝나면 지워지므로(아래 "수명"), 다음 멘션 때 살아 있는 표는 모두 사람이 출력으로 본 표다. 남는 위험은 모델이 같은 턴에 방금 만든 표(사람이 아직 못 본 표)에 번호를 쓰는 것이라, 코어가 **이번 턴에 만든 표에 `rows`·`exclude_rows`가 오면 거절**한다.
- **본 표가 여러 개일 때 기준**: 사용자가 유니 메시지에 답장했으면 그 메시지에 묶인 표, 답장이 아니면 마지막으로 보여 준 표의 번호로 본다. 코어가 프롬프트 조각에 `답장한 메시지의 표: t3`, `마지막으로 보여 준 표: t5`를 적어 주어 모델이 추측하지 않게 한다.
- 없는 번호(표가 9행인데 12번)는 에러로 돌려준다.
- **표 인자에 번호 붙이기 (2026-10-20 결정)**: 표를 받는 모든 인자(`TableRef`)는 `"t3"`뿐 아니라 `"t3:2,3"`도 받는다. 뜻은 `table_query(t3, rows=[2, 3])`로 고른 표를 넘긴 것과 같다. "2번 목표 지워줘"를 `delete_goals("t3:2")` 한 번으로 끝내 호출 수를 아끼려는 것이다. 문법은 `표 id` + `:` + 쉼표로 구분한 번호뿐이다(범위·빼기는 없다 — 그런 건 `table_query`로). 번호 규칙(이번 턴에 만든 표는 거절, 없는 번호는 에러)은 `rows`와 똑같이 적용한다. 번호로 고른 뒤에 도구의 "필요한 것" 확인과 빼기를 한다.

**슬래시와 같이 쓰기 (2026-10-20 결정).** 슬래시는 표를 쓸 수 없다(슬래시 결과 표는 보관하지 않고, 사람이 `t3`를 칠 수도 없다). 그래서 지금 id를 받는 도구는 **입구를 둘로 나눈다.**
- 슬래시 입구: `@slash_only`(모델에게 안 보이는 슬래시 명령)로 두고 지금처럼 id를 받는다. 사람은 슬래시 목록 결과의 `slash_only` 칸(id)을 보고 친다.
- 모델 입구: 슬래시 없는 새 도구가 id 대신 **표**(`TableRef`)를 받는다. 모델은 id를 아예 보지 못한다.
- 실제 일을 하는 로직은 스킬 안의 함수 하나로 두고 두 입구가 같이 부른다(설계 원칙 3).
- 항목 하나만 다루는 도구(목표 하나 수정 등)는 표에서 **정확히 한 행**이 남아야 한다고 선언하고, 아니면 "한 행만 골라야 한다" 에러를 낸다.
- 하나의 도구에 id 인자와 표 인자를 같이 두는 안은 모델에게 id 인자가 보여 다시 옮겨 적게 되므로 택하지 않았다. 슬래시도 번호를 받는 안은 슬래시가 표를 보관하지 않아 번호가 어느 목록의 것인지 알 수 없으므로 택하지 않았다.
- 어느 도구를 어떻게 나누는지는 `docs/plan/2026-10-20_수정.md` §16 Part 6에 있다.

- 조건 값은 모델이 숫자로 바꾸지 않는다. 그 칸의 값 종류가 `ScoreRef`면 `"SSS"`를 코어가 `ScoreRef` 해석기로 1,007,500으로 바꾼다. 랭크·램프·난이도도 같다.
- 값이 없는 행(안 친 채보의 점수 등)은 **어떤 조건이든 통과시킨다**(2026-10-20 임시 결정 — 나중에 칸이나 조건마다 정한다). 정렬에서는 방향과 무관하게 맨 뒤다.
- 숫자 규칙: 유니의 말 속 숫자는 모델이 실제로 받은 것(표 요약·`table_peek` 결과·다른 도구의 `data`)과 대조한다. 출력에만 있는 표 내용은 대조 대상에 넣지 않는다.

**글자 출력.**
- 멘션 한 턴에서 **마지막으로 만들어진 표 하나만** 코어가 그려 required 표시물로 붙인다. 중간 표는 그리지 않는다. `[[no_table]]`이면 뺀다. 그 표를 그림 표로 이미 그렸으면 글자로 다시 그리지 않는다(아래 "그림 표").
- 그리기는 코어의 공통 함수 하나가 맡는다. 머리말(`steps`, `summary`) 뒤에 묶음마다 표지 줄(`── 베스트 30 · 평균 17.04 ──`, `── 15.5 · 15채보 ──`)을 두고, 그 아래 행마다 한 줄(번호 + 행 글)을 쓴다. 이름 없는 묶음 하나뿐이면 표지 줄을 생략한다.
- **행 한 줄의 모양 (2026-10-20 결정).** 지금 목록 도구들이 직접 만들던 읽기 좋은 줄("크로노 MAS 15.2  1,005,000 → 1,007,500  (남은 2,500점)")을 공통 출력에서도 지키기 위해 세 가지를 함께 쓴다.
  1. **기본 출력은 "칸 이름 + 값", 빈 칸은 생략한다.** 예: `크로노 MAS  상수 15.2  점수 1,005,000  목표 점수 1,007,500`. 곡·난이도 칸은 이름 없이 값만 쓴다. 보일 글자가 비었거나 원래 값이 없는 칸은 줄에서 뺀다(`-`를 늘어놓지 않는다). 칸 이름이 없으면 숫자의 뜻을 알 수 없어서다.
  2. **원천 도구가 한 줄 서식을 줄 수 있다.** 예: `"{곡} {난이도} {상수}  {점수} → {목표 점수}  (남은 {남은 점수}점)"`. 코어는 `{칸 이름}` 자리에 그 칸의 보일 글자를 끼워 넣기만 한다(츄니즘을 모른다). 서식은 여러 개 줄 수 있고, 행마다 **서식에 쓴 칸이 모두 차 있는 첫 서식**을 쓴다. 맞는 서식이 없으면 기본 출력(1번). 서식에 없는 칸(나중에 다른 도구가 붙인 칸 등)은 줄 끝에 "칸 이름 + 값"으로 덧붙인다. `table_query`로 만든 표와 칸을 더한 표도 서식을 물려받는다.
  3. **글자 출력에서 숨길 칸을 표시할 수 있다**(`hidden_in_text`). 거르기·정렬에는 쓰지만 매 줄에 보일 필요는 없는 칸(예: 목표의 공개 여부)이다. 모델 요약의 칸 목록에는 그대로 나온다.
- 디스코드 코드 블록으로 칸을 세로로 맞추는 모양은 한글·일본어 글자 폭이 달라 줄이 어긋나고 폰에서 꺾여서 쓰지 않는다. 텍스트 파일도 메시지와 같은 줄 모양을 쓴다.
- **긴 표는 텍스트 파일로 (2026-10-20 결정).** 행이 기준(`TABLE_FILE_ROWS = 10`)을 넘으면(11행부터) 행 목록을 메시지에 펼치지 않고 `.txt` 파일로 첨부한다. 메시지 본문에는 유니의 말과 머리말만 남는다. 긴 목록이 채널을 여러 메시지로 덮어 다른 사람의 대화를 밀어내지 않게 하려는 것이다. 디스코드가 파일 앞부분을 접힌 미리보기로 보여 준다. 파일에는 행 수 상한이 없다. 페이지 버튼은 검토했지만 쓰지 않는다(사용자 결정).
- 기준 이하의 표는 메시지에 그대로 펼친다. 작업 표가 아닌 기존 긴 표시물은 지금처럼 나눠 보낸다.
- 슬래시 명령이 표를 돌려받으면 같은 함수로 바로 그려 보낸다. 파일 규칙도 같다. 슬래시로 만든 표는 보관하지 않는다.
- 파일을 붙이려면 표시물에 첨부 파일 자리(`Display.files`)가 있어야 한다. 멘션과 슬래시가 보내는 곳 두 군데가 이걸 실어 보낸다.

**그림 표 (2026-10-20 결정).**
- 새 스킬 `chunithm-image`의 도구 `table_image(table, layout)` 하나다. 기본 출력이 아니라 "그림으로", "레이팅표", "상수표로" 같은 요청이 있을 때만 모델이 부른다. 재킷을 받아야 해서 무겁다(`weight: heavy`).
- `layout`은 `card`(재킷 카드 격자 — 레이팅표·상수표 모양)와 `list`(한 줄에 재킷·제목·난이도·점수·랭크) 둘이다.
- 재킷, 난이도 색, 랭크 색은 츄니즘 전용이라 코어가 아니라 스킬에 둔다. 곡 칸이 차 있어야 한다고 선언하므로, 곡이 없는 행은 위 규칙대로 빠진다. 곡 단위 행(난이도 빈 값)은 난이도·상수·점수 없이 재킷과 곡 제목만 그린다.
- 묶음·표지·정렬·머리말은 표가 가진 그대로 그리고, 그림 도구는 배치만 고른다. 레이팅표 전용 머리말은 따로 두지 않는다 — `best`가 표 요약에 닉네임·레벨·레이팅을 넣는다. 캐릭터 그림은 표의 `subject` 플레이어의 저장된 프로필에서 찾는다(아래 "플레이어 레벨·캐릭터 그림").
- 그림 도구는 공통 칸 이름(위 "곡·난이도 칸")으로 칸을 알아본다. 있는 칸만 그린다(점수 칸이 없으면 카드에 상수만). 글자는 셀의 보일 글자를 그대로 쓴다.
- 카드·줄마다 글자 출력과 같은 행 번호(`#1`처럼)를 작게 찍는다. 그림만 본 사람도 "2번"으로 가리킬 수 있게 한다.

- 결과에 "이 표를 그렸다"는 표시(게임과 무관한 일반 장치)를 둔다. 코어는 그 턴의 마지막 표가 그렇게 그려졌으면 글자 자동 출력을 건너뛴다.

**플레이어 레벨·캐릭터 그림 (2026-10-20 결정).** 동기화 때 같이 저장한다. 동기화는 이미 프로필 페이지를 읽고(`SyncFetch.profile`), 그 안에 레벨(`level`)·환생 별(`reincarnation_stars`)·캐릭터 그림 주소(`profile_picture`)·캐릭터 프레임 주소(`profile_picture_frame`)가 있다. 지금은 닉네임과 레이팅만 쓰고 나머지를 버린다. 추가 접속 없이 저장만 하면 된다. 펭귄 아바타 부품(`user_avatar`)은 저장하지 않는다. **그림 파일은 받지 않고 주소만 저장한다**(2026-10-20 사용자 결정). 그림 표를 그릴 때 그 주소에서 받아 재킷과 같은 디스크 캐시에 둔다. 위 실험에서 캐릭터 그림과 프레임도 로그인 없이 받아져 그릴 때 받아도 된다.

**수명 (2026-10-20 결정).**
- 표는 플레이어+채널별로 메모리에만 둔다. 재시작하면 사라진다.
- 턴이 끝나면 출력한 표만 그 유니 답장 메시지(나눠 보냈으면 첫 조각)에 묶어 남기고, 중간 표는 버린다.
- 표는 묶인 메시지가 앞선 대화(플레이어 메시지 최대 10개, "대화 맥락" 참고) 안에 있는 동안 살아 있다. 멘션마다 코어가 맥락 안의 살아 있는 표를 프롬프트 조각으로 넣는다(`t3 — steps (9행, 칸: …)`). 그 플레이어+채널의 나머지 표는 그때 지운다.
- 대화 스레드 안에서는 스레드가 열려 있는 동안 살아 있다.
- 그 채널에서 다시 멘션하지 않으면 지울 계기가 없으니, 만든 지 24시간이 지난 표는 맥락과 무관하게 지운다(2026-10-20 결정).

**찍어 둔 값 (2026-10-20 결정).** 표는 만든 순간의 값을 들고 있고, 그 뒤 실제 데이터가 바뀌어도 따라 바뀌지 않는다. 값이 바뀌는 계기는 대부분 동기화(점수·랭크·램프·레이팅·목표 달성)이고, 그 밖에는 슬래시로 직접 바꾸는 것(목표 삭제, 메모 수정 등)이다. 세 규칙을 함께 쓴다.
1. **동기화되면 "옛 값" 표시를 단다.** 어떤 플레이어의 동기화가 저장되면, `subject`가 그 플레이어인 표에 모두 "옛 값" 표시가 붙는다. 표는 바꾸지 않으므로 표시는 표 자체가 아니라 보관소가 따로 기억한다. 표시가 붙은 표는:
   - 살아 있는 표 프롬프트 조각에 `t1 (동기화 전 값)`으로 보인다. 모델은 이걸 보면 그 표를 쓰지 않고 원래 도구를 다시 부른다(`rules.md` 지침).
   - 그 표로 `table_query`를 하면 결과 표도 "옛 값"이고, 글자 출력과 그림 표의 머리말에 "동기화 전 값"이 찍힌다.
   - `subject`가 없는 표(곡 검색 등)에는 붙지 않는다.
   - 코어는 츄니즘의 동기화를 모른다. 보관소는 "이 플레이어 데이터의 표에 옛 값 표시"라는 일반 기능만 열고, 동기화를 저장하는 쪽(`chunithm-sync`)이 저장 직후에 그 기능을 부른다.
2. **데이터를 바꾸는 도구(`mutates=True`)는 "옛 값" 표를 받지 않는다.** 실행기가 도구를 부르기 전에 막고 "표가 동기화 전 값이라 다시 만들어야 한다" 에러를 돌려준다. 모델은 표를 새로 만들어 다시 한다. 예: 14:00 표에서 "100만 안 되는 곡"을 골랐는데 14:30 동기화로 한 곡이 100만을 넘었다면, 그 곡이 투두로 들어가는 것을 막는다.
3. **데이터를 바꾸는 도구는 실행 직전에 지금 DB를 키로 다시 읽는다.** 이미 없어진 항목·이미 바뀐 항목은 실제로 바꿀 대상에서 빼고, 확인 화면과 결과에 "2개 중 1개는 이미 없음"처럼 실제로 바뀐 것만 말한다. 슬래시로 직접 바꾼 경우에는 1번 표시가 붙지 않지만, 이 규칙이 바꾸는 쪽을 지킨다.
- 동기화되면 표를 지우는 안은 "그중에…"가 갑자기 "그 표 없음"이 돼 헷갈리고, 표가 만들어진 과정을 기억했다가 다시 계산하는 안은 바꾸지 않는 표라는 원칙이 깨지고 복잡해서 택하지 않았다.

**흐름 예시.** "15 상수 마스 중에 SSS 못 한 거 노트 수 많은 순으로 보여줘"
1. `chunithm-song.find_songs(min_const=15.0, max_const=15.0, difficulty="MAS")` → `t1`(24행, 곡·난이도·상수·노트 수)
2. `chunithm-report.add_scores(table="t1")` → `t2`(점수·램프 칸 추가). `records`의 여러 채보 PB를 한 번에 조회한다.
3. `table_query(table="t2", where=[점수 < "SSS"], sort="노트 수", descending=true)` → `t3`
4. 유니: "SSS 못 한 건 9곡이야." → 코어가 `t3`만 그려 붙인다. 다음 멘션 "그중 AJ 한 건 빼줘"는 `table_query(table="t3", …)` 한 번이다.

"레이팅 전체 보여줘"는 `chunithm-report.best(kind="both")` 한 번이다. 결과는 "베스트 30 · 평균 …"/"신곡 20 · 평균 …" 두 표지의 50행 표에 요약(닉네임·레이팅)이 붙은 형태다. 유니는 요약의 레이팅만 말한다. 11행이 넘으니 행 목록은 텍스트 파일로 나간다. "레이팅표 그림으로"면 `table_image(table="t1", layout="card")`를 한 번 더 부른다.

"15 이상 마스 상수표 내 점수로 만들어줘"는 `find_songs(min_const=15.0, difficulty="MAS")` → `add_scores` → `table_query(group_by="상수", sort="점수", descending=true)` → `table_image(layout="card")`로 호출 4번이다(상한 5 안).

**첫 범위.**
- 표를 만드는 쪽: `chunithm-song`의 `find_by_const`·`find_by_version`·`find_songs`·`find_by_artist`, `chunithm-report.best`, `chunithm-folders`의 폴더 불러오기
- `find_by_artist`에 선택 인자 `difficulty`를 더한다. 난이도를 말했으면 그 난이도의 채보 행, 말하지 않았으면 **곡 단위 행**(난이도 칸 비움)을 만든다. MAS로 가정하지 않는다(2026-10-20 결정 — 앞서 정한 "기본 MAS"를 바꿨다).
- 표를 받는 쪽: `chunithm-report.add_scores`(새 도구), `chunithm-folders`의 표를 폴더로 저장하기(칸은 버리고 채보 목록만), `chunithm-image.table_image`
- `find_songs`의 `sort_by`/`descending`은 `table_query`와 겹쳐서 뺀다.
- 친 곡 전체를 레이팅순으로 보는 원천 도구는 만들지 않는다(2026-10-20 결정).
- 첫 범위 밖에서 표를 내거나 받을 도구 목록은 `docs/plan/2026-10-20_수정.md` §16 Part 4~6에 있다. 그대로 두는 도구와 그 이유도 거기 있다.

### 이벤트와 예약 작업

- `@on("chunithm.sync.completed")`: 다른 스킬이 낸 이벤트를 받는다. 핸들러는 `(ctx, payload)`를 받고, 반환 타입 힌트가 `Section`(또는 `Section | None`)이면 모으기, 아니면 알림으로 등록된다.
- `@schedule("0 9 * * *", catch_up=True)`: 예약 작업. `catch_up`은 새벽 정지 시간에 놓친 실행을 켜진 뒤 한 번 돌린다는 뜻이다.
- 이벤트 처리와 예약 작업도 도구와 같은 `display`를 내고, 필요하면 `ctx.yuni.line(...)`으로 유니의 한마디를 붙인다.
- `@prompt_context`: 유니를 부른 플레이어에 대해 짧은 맥락을 프롬프트에 넣는다. 스킬이 펼쳐지지 않아도 들어간다. 예: `yuni-bond`의 열린 약속. 스킬당 300자를 넘지 않고, 코어가 넘치는 부분을 자른다. 상태를 바꾸지 않고 읽기만 한다.
- `@slash_only`: 도구로 노출하지 않는 슬래시 명령. 쿠키 입력창이나 계정 연결처럼 LLM이 건드리면 안 되는 기능에 쓴다. 반환 타입 힌트가 `discord.ui.Modal`이면 코어가 defer 없이 바로 입력창을 연다(다른 슬래시 명령은 먼저 defer한다).

### 데이터와 설정

- 스킬 테이블은 이름이 스킬 이름에서 게임 접두사(`chunithm-`)를 빼고 하이픈을 밑줄로 바꾼 것으로 시작한다(`chunithm-goals` → `goals_`, `yuni-bond` → `yuni_bond_`, `account-link` → `account_link_`). 접두사가 겹치면 계약 테스트에서 걸린다. 게임에 딸린 테이블은 `game` 열을, 플레이어 데이터는 `player_id` 열을 둔다. 계정 연결로 한쪽 플레이어의 데이터를 버릴 때, 코어가 이 열로 모든 스킬 테이블의 행을 미리 세고 지운다.
- 마이그레이션은 스킬 폴더마다 따로 둔다. `migrations/001_init.sql`처럼 `번호_설명.sql` 파일을 두고, 봇이 시작할 때 코어가 아직 실행하지 않은 파일만 번호순으로 실행한다. 코어(`migrations/core/`)가 먼저, 스킬은 이름순이다. 파일 하나는 트랜잭션 하나로 돌리고, 실행한 파일은 `schema_migrations` 테이블(스킬, 파일 이름, 적용 시각, 내용 체크섬)에 남긴다. 실패하면 봇을 띄우지 않는다. 이미 적용한 파일은 고치지 않고 다음 번호 파일을 더한다. 적용한 파일의 내용이 바뀌면 체크섬으로 잡아 기동을 멈춘다.
- 다른 스킬의 테이블은 직접 읽거나 쓰지 않는다. 필요하면 서비스나 이벤트를 거친다.

### 예시: 보더 스킬

```markdown
---
name: chunithm-border
description: 곡과 난이도별 랭크 보더(허용 어택 개수)와 목표 점수까지 남은 어택을 계산한다.
examples:
  - 크로노 마스 SSS+ 보더 알려줘
  - 내 최고점에서 트플플까지 몇 어택 남았어?
category: 곡 정보
game: chunithm
version: 1
services: [songdb, records]
---

- 보더는 저스티스 0, 미스 0 기준의 허용 어택 개수만 말한다.
- 랭크 하나만 물으면 말로 답하고 표시물은 붙이지 않는다. 여러 랭크를 묻거나 "보더 보여 줘"라고 하면 붙인다.
- 표시물을 붙이면 숫자를 다시 나열하지 말고, 눈에 띄는 점 하나만 짚는다.
- 노트 수가 없는 채보는 계산 불가라고 말한다.
```

```python
@tool(slash="보더")
async def lookup(ctx: ToolContext, chart: ChartRef, rank: RankRef | None = None) -> ToolResult:
    """곡과 난이도의 랭크별 허용 어택 개수를 계산한다."""
    # chart는 코어가 이미 찾아서 넘긴 채보다. 난이도를 빼면 MAS로 본다.
    borders = ctx.records.attack_borders(chart.note_count, rank)  # records의 점수 유틸리티(순수 함수)
    return ToolResult(data=borders.as_dict(), display=border_embed(chart, borders), display_mode="optional")
```

## 스킬 불러오기

모델에는 평소에 스킬 카드(이름, 소개, 질문 예시)만 넣고, 모델이 고른 스킬만 펼친다. Claude 스킬의 단계별 로딩과 같은 생각이다.

1. **카드.** 코어가 켜진 스킬의 카드를 프롬프트에 넣는다. 스킬 16개면 대략 2천 토큰 안쪽으로 본다(한국어 소개와 예시 기준 추정).
2. **펼치기.** 모델이 `open_skill("chunithm-border")`을 부르면, 다음 호출부터 그 스킬의 본문 지침과 도구 정의가 들어간다. 질문 하나가 여러 스킬에 걸치면 여러 개를 한 번에 펼친다(`open_skill`은 스킬 하나만 받으므로 같은 턴에 병렬로 여러 번 부른다).
3. **참고 자료.** `reference/`의 긴 자료는 스킬이 제공하는 읽기 도구로만 들어간다.
4. **유지와 정리.** 펼친 스킬은 같은 대화(답장 사슬이나 스레드) 안에서 유지한다. 동시에 펼칠 수 있는 스킬 수에 상한을 두고, 넘치면 가장 오래 안 쓴 것부터 접는다.

**대가는 LLM 호출 한 번이다.** `open_skill`을 부른 뒤에야 실제 도구를 부를 수 있어서, 질문마다 왕복이 하나 늘어난다. 그래서 로딩 방식을 설정값 두 가지로 둔다.

| 방식 | 처음부터 넣는 것 | 펼칠 때 더하는 것 | 언제 |
| --- | --- | --- | --- |
| `instructions` | 카드 + 모든 도구 정의 | 지침만 | 도구가 적을 때. 왕복이 안 늘어난다. |
| `full` | 카드만 | 지침 + 도구 정의 | 도구가 많아 선택이 흔들리거나 토큰이 커질 때. |

시작은 `instructions`로 한다. 어느 지점에서 `full`로 바꿀지는 스킬 카드의 `examples`로 도구 선택 정확도를 재서 정한다. Gemini가 도구 몇 개까지 안정적으로 고르는지는 문서에서 찾지 못했으므로 직접 재야 한다.

**이벤트로 시작하는 일은 펼치지 않는다.** 동기화 리포트나 기한 알림처럼 코드가 시작하는 일은 스킬 코드가 직접 결과를 만들고, 유니의 한마디만 코어에 요청한다. 이때는 도구 없이 짧은 프롬프트 한 번으로 끝난다.

(구현: 펼친 스킬은 유니가 보낸 메시지 id마다 DB(`conversation_skills`, `migrations/core/016`)에 오래 안 쓴 순서로 남긴다. 그 메시지에 단 답장은 가장 가까운 유니 메시지의 목록을 이어받아 처음부터 펼친 채로 시작하고, 답장이 아닌 새 멘션은 새로 시작한다. 7일이 지난 행은 60초 폴링 루프가 지운다. 대화 스레드는 스레드 객체에 목록을 둔다. 동시에 펼칠 수 있는 수는 5개(`MAX_OPEN_SKILLS`)이고, 넘치면 가장 오래 안 쓴 것부터 접는다. 스킬의 도구를 쓰는 것도 "쓴 것"으로 친다.)

## 이벤트, 예약 작업, 서비스

스킬끼리는 서로를 직접 부르지 않는다. 공통으로 쓰는 기능은 서비스가 맡고, 스킬 사이의 연결은 이벤트로만 한다. 그래서 스킬 하나를 빼도 다른 스킬이 깨지지 않는다.

### 이벤트

두 종류다.

- **알림 이벤트**: 내고 끝난다. 받는 스킬이 없어도 된다. 받는 함수들은 동시에 돌고, 낸 쪽은 결과를 기다리지 않는다. 예: `players.linked`.
- **모으기 이벤트**: 받는 스킬들이 조각을 하나씩 돌려주거나 할 말이 없으면 없음을 돌려주고, 낸 스킬이 조각을 한 메시지로 묶는다. 예: `chunithm.sync.completed`.

| 조각의 칸 | 뜻 |
| --- | --- |
| `order` | 메시지 안에서의 순서. 작을수록 위다. 같으면 스킬 이름순이다 |
| `display` | 이 조각의 표시물. 없어도 된다 |
| `data` | 유니가 한마디를 만들 때 쓰는 숫자와 사실 |
| `hint` | 유니에게 주는 짧은 귀띔. 숫자는 `data`에 있는 것만 쓴다 |
| `stage` | 코드가 고른 반응 단계(`great`, `good`, `close`, `rest`). `yuni` 서비스는 조각들 중 가장 높은 단계를 쓴다 |

동기화를 예로 들면 이렇다. `chunithm-sync`가 `records`에 스냅샷을 저장하고 `chunithm.sync.completed`를 모은다. 리포트·목표·신곡·오락실 스킬이 조각을, `yuni-bond`가 표시물 없는 귀띔을 돌려준다. `chunithm-sync`는 조각을 순서대로 붙이고 `yuni` 서비스에 한마디를 한 번만 요청한 뒤, 보낸 내용을 담아 `chunithm.sync.reported`를 낸다. 세션 스킬이 이걸 받아 보관한다. 목표 스킬을 끄면 리포트에서 그 조각만 빠진다.

**규칙**

- **이름과 형식**: 이름은 `게임.영역.사건`(공통은 `players.사건`)으로 짓는다. 내용은 평문 dict이고(기존 이벤트가 모두 dict라 msgspec 구조체 대신 이렇게 통일했다), 각 key는 내는 쪽 스킬 문서의 이벤트 절에 적는다. 이벤트 이름은 manifest의 `emits`에 적는다. 서비스도 이벤트를 낼 수 있다. 아무도 내지 않는 이벤트를 받겠다고 적으면 계약 테스트에서 걸린다.
- **시간 제한**: 모으기 이벤트의 받는 함수는 기본 5초 안에 답해야 한다. 넘기거나 오류가 나면 그 조각만 빠지고 로그가 남는다. 다른 받는 쪽과 낸 쪽은 계속 돈다.
- **받기 전 검사**: 그 서버에서 스킬이 켜져 있는지, 이벤트 대상 플레이어가 그 스킬의 태그 조건을 갖췄는지, 연쇄 깊이가 3을 넘지 않는지를 코어가 본다.
- **메모리 안에서만**: 이벤트는 저장하지 않는다. 도중에 봇이 꺼지면 그 이벤트는 사라진다. 재시작에도 살아야 하는 일은 DB에 저장되는 예약 작업으로 한다.
- **형식이 바뀔 때**: 칸을 더하는 것은 괜찮다. 칸을 빼거나 뜻을 바꾸면 이름에 버전을 붙인다. 예: `chunithm.sync.completed.v2`.
- **콜백과의 구분**: 대화 스레드가 닫히면 코어는 스레드를 연 스킬에 대화 전문을 직접 돌려준다. 이것은 이벤트가 아니다.

**이벤트 목록**

| 이벤트 | 종류 | 내는 곳 | 받는 스킬 |
| --- | --- | --- | --- |
| `players.first_seen` | 알림 | 코어 | `yuni-bond` |
| `players.linked` | 알림 | `account-link` | 없음 |
| `chunithm.login.expired` | 알림 | `chunithm_net` 서비스 | `chunithm-account` |
| `chunithm.sync.completed` | 모으기 | `chunithm-sync` | `chunithm-report`, `chunithm-goals`, `chunithm-updates`, `chunithm-arcade`, `yuni-bond` |
| `chunithm.sync.reported` | 알림 | `chunithm-sync` | `chunithm-session` |
| `chunithm.song.viewed` | 모으기 | `chunithm-song` | `chunithm-notes`, `chunithm-goals`, `yuni-bond` |
| `chunithm.session.viewed` | 모으기 | `chunithm-session` | `chunithm-arcade` |
| `chunithm.session.closed` | 알림 | `chunithm-session` | 없음 |
| `chunithm.goal.completed` | 알림 | `chunithm-goals` | `yuni-bond` |
| `chunithm.plan.requested` | 모으기 | `yuni-bond` | `chunithm-goals`, `chunithm-notes` |

받는 스킬이 없는 이벤트는 나중에 더할 스킬을 위해 내 둔다.

### 예약 작업

- 예약은 DB에 저장해서 재시작에도 남는다. 기한 알림처럼 한 번 도는 예약과, 공지 확인처럼 주기적으로 도는 예약을 같은 표에 둔다.
- 예약 시각은 새벽 정지 시간대(설정값, 기본 02시\~06시) 밖으로 잡는다. 예기치 않게 꺼져 있었다면 켜질 때 `catch_up`이 켜진 예약 중 그날 것만 보낸다. 꺼져 있는 동안 온 멘션에는 켜진 뒤에도 답하지 않는다.
- 구현 상태(9단계 Part 1): 기동 때 `catch_up`에 더해, `core/bot.py`의 `YuniClient`가 60초마다 도는 폴링 루프(`_poll_schedules`, `discord.ext.tasks.loop`)로 운영 중에도 돈다 — `startup_catch_up`류와 달리 "오늘" 제한·`catch_up` 플래그를 안 보고, 지금 된 것을 바로 돈다(`Scheduler.poll_due_recurring`/`poll_due_once`). 예약 상태는 `(스킬, 함수 이름)`으로 저장하고, 예약 작업의 `ctx.player_id`는 `"system"`이다. 자정을 걸치는 정지 시간대는 지원하지 않는다.
- 스킬이 한 번짜리 예약을 걸려면(기한 알림 등) `ctx.scheduler`(`core/scheduler.py`의 `Scheduler`)를 쓴다. `db`/`player_data`/`registry_snapshot`/`usage`와 같은 ToolContext 전용 필드라, manifest의 `services`에 `scheduler`를 적어야 접근할 수 있다(`core/registry.py`의 `CTX_FIELD_SERVICE_NAMES`). `schedule_once(...)`가 돌려주는 행 id로 `cancel_once(id)`를 불러 기한 전 달성처럼 더는 필요 없어진 예약을 지울 수 있다. `schedule_once`도 `fire_at`이 정지 시간대에 걸리면 자동으로 민다.

## 데이터, 권한, 비밀 값

지켜야 할 것은 clal 쿠키, 남의 기록, LLM에 들어가는 외부 글 세 가지다. 이 규칙들은 스킬 코드가 아니라 코어와 서비스가 지킨다. 스킬을 새로 쓰는 사람이 규칙을 잊어도 새지 않게 하려는 것이다.

**DB 구분** (SQLite, 하나의 파일)

| 출처 | 테이블 예 | 누가 쓰나 |
| --- | --- | --- |
| 코어 | 플레이어, 디스코드 계정, 설정, 메모리, 예약, 스킬 상태 | 코어와 공통 서비스 |
| 츄니즘 서비스 | 기록 스냅샷, 베스트, 곡 DB 캐시, 별칭, 암호화된 쿠키 | 서비스만. 스킬은 서비스 API로 읽는다 |
| 스킬 | `goals_*`, `arcade_*`, `session_*` 등 | 그 스킬만 |

**권한**

- 누구의 데이터를 쓸지는 코어가 정한다. 플레이어 인자는 `PlayerRef` 타입으로만 받는다. 공개 설정 검사는 그 데이터를 읽는 스킬 코드가 남을 조회할 때 한다(LLM에 맡기지 않는다).
- 다른 사람의 기록은 그 사람이 공개한 경우만 보인다. 메모와 목표는 기본 비공개, 동기화 리포트는 플레이어별 설정이고 기본은 채널 공개다. 본인이 채널에서 자기 기록을 요청하면 공개 설정과 상관없이 그 채널에 답한다.
- 바꾸는 도구는 요청한 플레이어 본인의 데이터만 바꾼다(서버 공유 데이터는 mutates 설명의 예외를 따른다). 여러 건을 바꾸거나 지우면 확인 버튼을 거친다.
- 디스코드 계정 연결과 해제는 account-link 스킬의 슬래시 명령과 버튼으로만 한다. 도구로 만들지 않는다.
- 스킬은 manifest의 `services`에 적은 서비스만 `ctx`로 받는다. 자기 스킬이 정의한 설정(manifest의 `settings`)을 읽을 때도 `settings`를 다른 서비스와 똑같이 `services`에 선언해야 `ctx.settings`를 받는다. 다른 스킬의 설정은 읽지 않는다 — 예외는 `admin`의 "보고 채널"처럼 admin.md가 "스킬 전용이 아니라 다른 스킬이 재사용할 수 있게" admin 설정으로 두기로 명시한 경우뿐이다(`admin.md` "구현 결정", `chunithm-terms`가 첫 소비자).

**권한 태그**

스킬과 도구를 쓸 수 있는지는 플레이어가 가진 태그로 정한다. 태그는 서로 독립이라 위아래가 없다. 그래서 "관리자이지만 CHUNITHM-NET은 연동하지 않은 사람"은 `admin` 태그만 가진 플레이어로 그대로 표현된다.

| 종류 | 예 | 누가 붙이나 | 없는 사람에게 |
| --- | --- | --- | --- |
| 부여 태그 | `admin`, `tester` | 관리자가 `admin` 스킬로. 첫 관리자는 `.env`에 적은 디스코드 ID | 숨긴다. 카드와 안내에서 빠진다. 슬래시 목록에는 보이지만(디스코드에서 막을 수 없다) 실행하면 안내 없이 "모르는 명령"으로만 답한다 |
| 상태 태그 | `chunithm-linked`, `chunithm-synced` | 서비스가 상태를 보고 자동으로. 로그인 성공, 쿠키 만료, 첫 동기화 | 보이되 잠긴다. "CHUNITHM-NET 로그인하면 쓸 수 있어요"처럼 얻는 방법을 안내한다 |
| 스킬 태그 | 예: `goals-beta` | 스킬이 `defines_tags`로 정의하고, 관리자가 붙인다 | 정의할 때 숨길지 안내할지 고른다 |

- **조건 적는 법**: `tags: [a, b]`는 둘 다 있어야 한다. 하나만 있어도 되면 `tags_any: [a, b]`를 쓴다. 도구의 `tags`는 스킬의 조건에 더해진다.
- **검사하는 곳**: 프롬프트 조립(카드 거르기), 도구 실행기(호출 직전), 슬래시 경로 세 곳이 같은 함수를 쓴다. 예약 작업과 이벤트 처리는 대상 플레이어의 태그로 검사한다.
- **태그는 플레이어에 붙는다.** 연결된 디스코드 계정은 모두 같은 태그를 갖는다.
- **상태 태그와 부여 태그의 구분**: 종류 열을 두지 않고 상태 태그 이름 집합(`core/permissions.py`의 `STATUS_ONLY_TAGS`)으로 구분한다. 상태 태그는 서비스 전용 메서드로만 바뀌고 admin이 붙이거나 뗄 수 없다. `defines_tags`로 정의한 태그는 모두 admin이 붙이고 뗄 수 있다.
- **`full` 모드의 도구 태그**: 펼친 스킬의 도구 선언은 도구 수준 태그로 숨기지 않는다. 태그가 없는 사람이 부르면 실행기가 막고 그 안내가 모델에 돌아간다. 카드는 스킬 수준 `tags`/`tags_any`로만 거른다.
- **정의 없는 태그는 못 쓴다.** 태그는 코어, 서비스, 스킬에서 정의하고 레지스트리에 모인다. 정의되지 않은 태그를 조건으로 쓰는 스킬은 계약 테스트에서 걸린다.
- **더 세분화할 때**: 서버별 태그나 디스코드 역할 연동이 필요해지면, 태그를 얻는 경로만 더한다. 스킬 쪽 조건 문법은 그대로다.

**비밀 값**

- clal 쿠키는 암호화해 저장하고, 복호화는 `secrets`와 `chunithm_net` 서비스 안에서만 한다. 스킬, 로그, LLM 입력에는 들어가지 않는다.
- 디스코드 토큰, LLM 키(`GEMINI_API_KEY`/`ANTHROPIC_API_KEY`), 암호화 키(`COOKIE_ENCRYPTION_KEY`, `Fernet.generate_key()` 값, 키 회전 없음), 첫 관리자(`ADMIN_DISCORD_IDS`)는 `.env`에서 읽는다. 암호화 키가 비어 있으면 `secrets` 서비스 없이 기동한다.
- 웹 검색 결과와 다른 사람이 쓴 글(메모, 후기)은 인용 데이터로만 모델에 넘긴다.

**한계.** 스킬은 같은 프로세스에서 도는 파이썬 코드라 샌드박스가 아니다. 위 규칙은 실수를 막는 장치이고, 악의적인 코드를 막지는 못한다. 지인 서버 규모에서는 저장소에 들어오는 스킬을 검토하는 것으로 충분하다고 본다.

**백업.** SQLite 파일과 암호화 키를 따로 보관한다. 키를 잃으면 모두 다시 로그인해야 한다.

## 유니 인격

멘션 응답과 유니의 한마디는 모두 유니 한 명의 말투로 내보내고, 말투가 사실과 숫자를 바꾸지 못하게 규칙 파일과 말투 파일을 나눈다. 유니를 명령을 받는 봇이 아니라 이 서버에 와 있는 서포터로 느끼게 하는 것이 목표다.

**확인된 캐릭터 특징** ([츄니즘 위키 유니 문서](https://wikiwiki.jp/chunithmwiki/%E3%83%A6%E3%83%8B), 2026-09-29 수정판 저장본)

- Linked VERSE의 내비게이터를 맡는 캐릭터이고, 곁에 파트너 나비가 함께 있다. 안내 역할의 봇과 설정이 맞는다.
- 일러스트는 煎茶, 성우는 希水しお다. 게임 안에서는 Linked VERSE 모드와 시스템 보이스에 음성이 있다.
- 츄니즘 10주년 기념 사이트에 먼저 등장했고, 공식 X 계정 아이콘을 츄니 펭귄 대신 맡았다.
- 캐릭터 랭크업 스토리는 없다. 이야기는 Linked VERSE 대사에만 있다.
- 1인칭은 "私"이고, 플레이어는 "プレイヤーさん", 파트너는 "ナビちゃん"이라고 부른다.
- 밝고 들뜬 반말에 늘임표와 느낌표가 많다. 종료 인사는 "シーユーネクストプレイ！"다.

**랭크별 반응** (시스템 보이스의 결과 화면 대사 11단계를 성격만 요약)

| 랭크 | 반응의 성격 |
| --- | --- |
| SSS, SSS+ | 크게 감탄하며 이 곡을 다 파악한 것 아니냐고 묻는다 |
| SS, SS+ | 넋 놓고 봤다며 손놀림을 칭찬한다 |
| S, S+ | 나비에게 봤냐고 호들갑을 떨고, 이제 자기 서포트에서 졸업이라며 아쉬워한다 |
| AAA | 좋다고 하면서 더 위 랭크도 보고 싶다고 한다 |
| AA | 점수가 늘었다고 해 주고 더 갈 수 있지 않냐고 부추긴다 |
| A | 해냈다며 자기 서포트 덕이라고 으쓱한다 |
| BBB | 한 걸음 남았다며 세팅을 다시 보자고 권한다 |
| BB | 조금만 더라며 나비와 함께 분석하자고 한다 |
| B | 한 걸음 전진했고 늘 여지가 많다고 한다 |
| C | 난이도를 바꿔 볼지 묻지만, 안 들을 걸 알고 응원한다 |
| D | 그런 날도 있다며 오늘은 쉬자고 한다 |

**봇에서의 반응 단계**

이 서버의 플레이어는 대부분 SS 이상을 내므로 절대 랭크만 쓰면 위쪽 반응만 반복된다. 원작의 단계 구조는 살리되 개인 기준으로 고른다. 단계는 스킬의 코드가 고르고 조각의 `stage`로 넘긴다.

| 단계 | 원작 계열 | 고르는 상황 (예) | 이어지는 말 |
| --- | --- | --- | --- |
| `great` | SSS·SS: 크게 감탄 | 개인 최고 갱신, 신규 SSS 이상, 목표 달성 | 없음 |
| `good` | AAA·AA: 인정하고 더 위를 부추김 | 같은 상수대의 평소 점수 수준 | 목표 랭크까지 남은 점수 안내 |
| `close` | BBB·BB: 세팅 점검과 분석 제안 | 목표에 조금 못 미침 | 분석 제안 |
| `rest` | C·D: 난이도 조정이나 휴식 권유 | 평소보다 크게 낮음, 진행이 거의 없음 | 낮은 상수의 곡이나 더 작은 목표 제안 |

**프롬프트 파일**

- `persona.md`(말투 파일): 인격 설명, 짧은 예시 몇 개, 유니 자신의 설정(좋아하는 것, 말버릇, 모르는 것). 대사집을 통째로 넣지 않는다. 유니의 설정을 고정해 두어 LLM이 그때그때 새 설정을 지어내지 못하게 한다.
- `rules.md`(규칙 파일): 도구 사용, 숫자, 출처, 남이 쓴 글의 취급. 말투 파일보다 우선한다.
- 말투는 이 파일 하나만 정한다. 스킬의 `SKILL.md`에는 말투를 쓰지 않는다.

**말투 규칙**

- 칭찬은 도구 결과로 확인된 성과에만 한다. 신규 SSS, To-Do 달성, 레이팅 갱신이 해당한다.
- 나쁜 소식과 부족한 점수는 돌려 말하지 않고 숫자 그대로 전한다. 미달을 탓하지도 않는다.
- 기능을 자기 일로 말한다. "명령어를 쓰세요"가 아니라 "내가 찾아볼게"라고 한다. 도구 실패, 쿨다운, 비용 상한도 유니의 사정으로 말하되, 원인과 해결 방법은 정확히 전한다.
- 원작 설정이 내비게이션 AI이므로, AI냐는 질문에는 숨기지 않고 그렇다고 답한다.
- Linked VERSE 스토리는 플레이어가 묻기 전에는 꺼내지 않는다.
- 나비는 화자로 나오지 않는다. 유니가 이름을 언급하는 것은 된다.
- 한국어 말투는 직접 정한다. 국제판에 공식 한국어 대사가 있는지는 확인하지 못했다. 말투 파일의 예시로 쓸 원문은 저장본에서 직접 옮긴다.
- LLM 장애 때 나가는 고정 문구(`core/fallback_messages.py`)도 유니 말투로 써 둔다.
- **구현 결정 (2026-10-19, 11단계)**: 말투는 밝은 반말로 정했다(원작이 반말이고 지인 서버라서). 한마디는 `yuni` 서비스가 `SUMMARY_MODEL`로 만든다. 프롬프트는 `rules.md` + `persona.md` + 한마디 지침이고, 입력은 조각의 `stage`·`data`·`hint` JSON이다. 호출이 실패하거나, 빈 응답이거나, 200자를 넘거나, `data`에 없는 숫자가 있으면 정해진 문구로 되돌린다(2026-10-20부터 단계별 문구 없이 중립 문구 하나 — 아래 "고정 문구 제거"). 사용량은 `kind="yuni_line"`으로 기록하며 `line()`에 `player_id`·`guild_id`를 넘긴 호출만 기록한다(`chunithm-sync`·`chunithm-goals`는 넘긴다. 서버 전체 알림인 `chunithm-updates`는 플레이어가 없어 기록하지 않는다). 호칭("~상")은 persona.md에 규칙만 있고 실제 호칭을 넘기는 일은 12단계다.
- **말투 조정 (2026-10-20)**: 원작 대사 원문(`docs/persona/yuni-lines/`)을 근거로 `persona.md`를 고쳤다. 소리 늘임·물결표·감탄사·나비짱 언급·으쓱하고 공 돌리기를 넣되 한 답에 한 번 정도로 제한하고, 사과·도구 실패·나쁜 소식에서는 늘임과 장난을 뺀다. 느낌표는 문장마다 하나까지(크게 감탄할 때만 "!!"). 호칭은 부를 이름이 없으면 "플레이어상"(원작 プレイヤーさん)을 답에 한 번 정도 쓴다. 10년 뒤의 유니 대사는 자료에서 뺐다.
- **말투 재조정 (2026-10-20, 같은 날 두 번째)**: 처음 고친 판은 "한 답에 한 번 정도" 같은 제한 때문에 실기에서 변화가 거의 안 보였다. 사용자 요청으로 `persona.md`를 10줄 미만으로 줄이고 구체적으로 다시 썼다 — 늘임이나 감탄사를 거의 모든 답에 하나 이상 넣고(숫자 답·사과·실패·나쁜 소식은 예외), 반응의 결 표와 예시는 한 줄씩으로 압축했다. 예시 20개로 늘리는 안은 10줄 제한과 맞지 않아 접었다.
- **잡담 형식·생각 노출 방지 (2026-10-20, 실기)**: 근황 잡담에 "대다아안해"식 과한 칭찬과 격려·마무리 인사가 붙고 대화가 끝나는 듯한 느낌이 났다. 잡담은 한마디 반응(전에 들은 일이 있으면 회상) + 다음 말을 끌어내는 질문 하나로 하고, 작별 인사는 플레이어가 끝내자고 했을 때만 쓰게 `persona.md`를 고쳤다. `rules.md`에는 "계획·규칙·도구 이름을 답에 쓰지 않는다"를 넣고 `GeminiLlmAdapter`는 `thought` part를 답 텍스트에서 뺀다.
- **감탄사 편중 (2026-10-20)**: 실기에서 "얏호"가 어울리지 않는 말에도 자주 나왔다. 감탄사 목록 + 예시에 같이 들어 있던 탓으로 보고, 감탄사를 상황별로 짝지어 주고 "얏호"는 반갑게 맞이하는 인사에만 쓰게 했다. 예시·안내 문구에서도 뺐다. 다른 감탄사도 편중되면 같은 방식으로 짝지어 준다.
- **안내 문구 (2026-10-20)**: `core/fallback_messages.py`의 고정 문구(답이 늦을 때, 찾아보는 중, 쿨다운, 상한, 실패, DM 실패)와 대화 끝내기·유휴 확인 문구(`ENDED_MESSAGE`·`IDLE_CHECK_MESSAGE`)를 새 말투(늘임·감탄사, 사과는 짧게)로 고쳤다. 유휴 확인은 존댓말("다 끝났나요?")이던 것을 반말로 맞췄고 상수로 옮겼다. 같은 말 반복을 줄이려고 상황마다 변형 5개(`*_MESSAGES`)를 두고 `pick`으로 무작위로 고른다(사용자 결정).
- **고정 문구 제거 (2026-10-20)**: 한마디의 단계별 고정 문구(`great`·`good`·`close`·`rest`마다 하나씩)를 없앴다. `stage`는 결과가 어땠는지의 표시로만 넘기고, 한마디 지침이 `data`·`hint`에서 구체적인 것 하나를 짚어 매번 새로 만들게 한다. LLM이 없거나 실패하면 단계와 상관없이 `fallback` 또는 중립 문구 "확인했어!"다.
- **설정집 (2026-10-20)**: `skills/yuni-lore/lore.md`에 유니·나비·용어·줄거리를 우리말로 정리했다(1단계 기본 / 2단계 중반 / 3단계 결말 스포일러). `persona.md`에는 요약 몇 줄만 넣고, 자세한 설정은 플레이어가 물을 때만 읽게 하는 것이 목표다 — 읽는 스킬 `yuni-lore`(15단계)가 구간(게이트) 단위로 읽어 준다. 결말 쪽 구간은 `spoiler_ok`가 있어야만 나간다.

* 표시물은 항상 정식 표기(SSS+, MAS)를 쓴다. 유니의 말은 플레이어가 쓴 표현을 따라갈 수 있다. 예: "트플플까지 3.20어택이에요."

**호칭**

1. 메모리의 호칭 칸
2. CHUNITHM-NET 닉네임 (동기화된 프로필에서 가져옴)
3. 디스코드 서버 닉네임 (연결된 계정이 여럿이면 말한 계정의 것)

정해 둔 호칭이 있으면 그대로 부른다. 닉네임으로 부를 때는 뒤에 "상"을 붙인다. 원작의 "プレイヤーさん"을 따른 것이다. 코드가 최종 부를 이름 하나(예: "디짐상")를 만들어 프롬프트 맥락에 넣고, 모델은 "상"을 직접 붙이지 않는다. 멘션 응답은 세 순위를 다 쓰고, 유니의 한마디(동기화 리포트·알림)는 말한 메시지가 없으므로 1·2순위만 쓴다. 어느 쪽도 없으면 부르지 않는다.

**표기**: 봇 소개에 비공식 팬 제작임을 적고, 공식 음성과 일러스트 파일은 재배포하지 않는다.

## 멘션 에이전트 규칙

유니는 부른 사람에게만 답하고, 멘션이 없는 일반 대화에는 끼어들지 않는다. 부르지 않은 메시지는 LLM에 넘기지도 않는다.

**유니가 말하는 조건**

| 계기 | 유니의 동작 |
| --- | --- |
| 유니를 멘션한 메시지 | 에이전트로 응답 |
| 유니의 메시지에 단 답장 | 멘션 알림이 켜진 답장만 응답 |
| 유니가 낸 버튼과 입력창 | 누른 사람에게만 이어서 응답 |
| 스킬이 연 대화 스레드 | 그 플레이어의 메시지에 멘션 없이 응답. 스레드가 닫히면 끝 |
| 슬래시 명령 | 명령 결과를 냄. LLM을 거치지 않음 |
| 예약된 알림 | 기한 알림과 업데이트 알림만. 메시지에 대한 반응이 아니라 일정에 따른 것 |
| 그 밖의 모든 메시지 | 반응하지 않고 LLM에도 넘기지 않음 |

**대화 맥락**

- 같은 채널에서 유니와 주고받은 최근 몇 턴만 넘긴다. 답장으로 이어진 대화는 그 사슬을 따른다. 멘션이 없는 메시지는 맥락으로도 모으지 않는다.
- 길이는 플레이어 메시지 수(지금 멘션 포함 최대 10, `MAX_CONTEXT_PLAYER_MESSAGES`)로만 센다. 유니 메시지는 세지 않는다 — 긴 답을 나눠 보낸 세 메시지도 플레이어 한 턴에 딸린다. 남긴 가장 오래된 플레이어 메시지보다 앞선 유니 메시지는 잘린 질문의 답이라 같이 뺀다(2026-10-20 결정). 채널 기록은 최근 50개를 읽어 거기서 고른다.
- 슬래시와 멘션 모두 2000자를 넘는 본문은 줄 경계에서 나눠(`core/message_split.py`) 이어 보낸다. 슬래시는 첫 조각만 원래 응답 자리로, 나머지는 팔로업으로 간다(2026-10-20 — 전에는 슬래시가 나누지 않아 긴 표시물이 통째로 거절될 수 있었다).
- 대화 기록은 저장하지 않는다. 오래 남길 내용은 메모리 요약으로만 남는다. 예외는 대화 스레드로, 전문을 연 스킬에 넘긴다.

**제한과 장애**

- 에이전트 반복 상한은 설정값 둘이다: 도구 호출 `MAX_TOOL_CALLS_PER_TURN`(기본 5), 토큰 `MAX_TOKENS_PER_TURN`(기본 50,000). 넘으면 멈추고, 모델이 낸 글이 있으면 그것을, 없으면 고정 문구를 보낸다.
- 플레이어별 쿨다운과 월 비용 상한은 멘션 경로에서만 집행한다. 쿨다운은 메모리에만 두어 재시작하면 풀린다. 월 상한은 서버별 설정이라 DM에는 없다.
- LLM 호출이 실패하거나 월 상한에 닿으면 유니 말투의 고정 문구로 슬래시 명령을 안내한다. 슬래시 명령은 LLM 없이 계속 동작한다. Gemini 일시 오류(429·500·502·503·504)는 2초·4초·8초 간격으로 최대 세 번 재시도한 뒤 고정 문구로 간다(`core/gemini_retry.py`, 2026-10-18 도입). 요청마다 타임아웃을 둔다(에이전트 30초, 검색 60초). 모델이 응답 없이 멈추면(2026-10-19 gemini-3.8-flash) 서버가 504로 끊고, 504는 한 번만 재시도한다. **보조 모델 (2026-10-20)**: `.env`의 `FALLBACK_MODEL`(선택, Gemini 제공자일 때만, 예 `gemini-3.5-flash-lite`)이 있으면 메인 모델이 재시도 끝에 일시 오류로 실패했을 때 같은 요청을 보조 모델로 한 번 더 보낸다. 이때 504는 같은 모델로 다시 기다리지 않고 바로 넘긴다(최악 62초 → 약 30초). 400 같은 요청 오류는 넘기지 않는다. 보조 모델이 답한 턴은 그 모델 요금으로 사용량을 기록한다. 대화 중간(함수 호출 뒤)에 넘어가면 메인 모델의 thought signature가 담긴 기록을 보조 모델이 받는다 — 거부되면 기존처럼 고정 문구로 간다. 한마디·요약(`SUMMARY_MODEL`)과 검색에는 아직 적용하지 않았다.
- 멘션 응답은 수 초가 걸리므로 처리 중에는 입력 중 표시를 띄운다. `weight: heavy`로 표시한 스킬의 도구를 부르는 순간 "확인하고 있다, 잠깐만 기다려 달라" 안내를 바로 보낸다(이번 요청에서 한 번만 — 503 재시도 안내와도 겹치면 둘 중 하나만). `light`(기본)인 스킬만 쓰인 턴은 아무리 오래 걸려도 이 안내를 보내지 않는다(2026-10-18 결정 — 전에는 20초 타이머로 판단해서 도구 2개 이상 부르는 평범한 턴에도 거의 매번 떴다).

**할 수 있는 일 안내** (`list_capabilities`)

- 근거는 등록된 스킬의 카드(소개, `category`, `examples`, 슬래시 명령, `tags`) 하나다. 유니는 여기에 없는 기능을 말하지 않는다. 스킬을 더하거나 빼면 안내도 같이 바뀐다.
- "뭐 할 수 있어?"에는 분류별로 한 줄씩 짧게 소개하고 분류를 고르는 버튼을 낸다. 첫 답은 한 화면을 넘기지 않는다.
- 그 플레이어가 지금 쓸 수 있는 것과, 상태 태그를 얻으면 쓸 수 있는 것(예: 로그인하면)을 나눠 보여 준다. 부여 태그가 없는 스킬은 보여 주지 않는다.
- 처음 멘션한 플레이어에게는 짧게 자기소개를 하고 로그인부터 안내한다. 코드 분기가 아니라 프롬프트 맥락 한 줄("이 플레이어는 유니를 처음 멘션했다")로 넣고 `rules.md`가 처리한다.
- 못 하는 일도 적어 둔다. 일본판 계정 동기화, 멘션 없는 대화에 끼어들기, 꺼져 있는 새벽 시간의 응답, 말만 듣고 디스코드 계정 연결하기, 한 플레이어가 CHUNITHM-NET 계정 여러 개 쓰기.
- 슬래시 `/도움말`도 같은 목록을 LLM 없이 보여 준다.

## 플레이어 메모리

플레이어마다 짧은 메모리 문서 하나를 두고, 대화가 끝날 때 LLM이 자동으로 요약해 갱신한다. 사실 위주의 프로필이고, 날짜가 있는 사건과 약속은 `yuni-bond`의 테이블에 따로 둔다. 보기·지우기·끄기는 `memory` 스킬이 맡는다.

- **저장 형식**: 플레이어당 본문 한 덩어리(상한 1,500자, 한 줄에 사실 하나)와 **호칭 한 칸**(상한 20자). 호칭은 본문과 따로 저장하고 길이 상한에도 넣지 않는다. 본문은 게임별 구획을 둘 수 있다. 플레이어가 지운 항목은 `forgotten`에 따로 남겨 요약이 되살리지 않게 한다(상한 500자, 넘으면 오래된 것부터 버림).
- **갱신 시점**: 그 플레이어의 멘션 응답 뒤 5분간 대화가 이어지지 않으면, 싼 모델(`SUMMARY_MODEL`) 호출 한 번으로 기존 메모리와 이번 대화에서 본인이 쓴 글을 합쳐 본문과 호칭을 다시 쓴다. 5분 안에 다시 말하면 기다리는 시간이 새로 시작된다. 대기 목록은 DB(`player_memory_pending`)에 두어 꺼지면서 못 한 요약을 켜진 뒤 이어서 한다. 확인은 기존 60초 폴링 루프가 한다. 자동저장이 꺼져 있으면 대기 목록에 넣지 않는다. 대화 스레드가 닫히면 그 전문(본인 글)을 같은 대기 목록에 한꺼번에 넣는다. 스레드 안의 답장마다 따로 넣지는 않는다.
- **저장 대상**: 호칭, 목표, 약한 패턴, 선호하는 답변 길이처럼 잘 변하지 않는 게임 관련 사실.
- **저장 제외**: 레이팅과 점수처럼 변하는 값(매번 도구로 조회), 게임과 무관한 개인사, 플레이어가 지운 항목.
- **출처 제한**: 본인(연결된 계정 포함)이 쓴 메시지에서만 뽑는다. 남이 그 사람에 대해 한 말과 농담은 넣지 않는다. 대기 목록에는 코드가 거른 본인 메시지만 쌓고, 유니의 말과 남의 말은 넣지 않는다.
- **주입 범위**: 요청한 본인의 메모리만 프롬프트에 넣는다.
- **용량 관리**: 상한을 넘으면 오래되고 겹치는 항목부터 합친다. 모델이 상한을 넘겨 돌려주면 코드가 맨 앞 줄부터 잘라 맞춘다.
- **저장 표시**: 요약이 메모리를 바꾸면 그 대화의 마지막 메시지에 반응 이모지 하나를 단다.
- **직접 기억**: "이거 기억해 줘"는 코어 도구 `remember`가 바로 저장한다. 호칭이면 `nickname`을 넘겨 호칭 칸에 저장한다. 기억해 달라고 한 항목이 `forgotten`에 있으면 그 항목을 `forgotten`에서 뺀다.
- **구현 결정 (2026-10-19, 12단계 Part 2)**: 대화 스레드는 `ThreadManager`가 디스코드 채널 id(`ThreadSession.channel_id`, 스레드나 DM)로 대화를 찾는다. `on_message`는 그 채널에서 그 대화의 플레이어(연결된 어느 계정이든)가 쓴 글이면 멘션 없이 같은 멘션 파이프라인(`MentionEntry.handle(thread=...)`)으로 답하고 전문에 쌓는다. 스레드를 연 스킬은 시작부터 펼친 채로 이어지고, 쿨다운·월 상한은 멘션과 같다. 닫히는 이유는 `explicit`·`timeout`·`shutdown`이고, 코어의 `on_closed` 처리(메모리 요약 대기 등록)가 연 스킬의 `on_close`보다 먼저 돈다. 무응답 점검은 60초 폴링 루프가 한다. 끝났다는 말을 알아듣는 일과 끝내기 버튼은 Part 3에서 코어에 더했다(아래). `YuniService.summarize_conversation`은 메모리 요약 경로와 같은 일이라 없앴다. `@prompt_context`는 `AgentLoop`가 응답마다 모아 프롬프트의 "맥락"에 넣는다(스킬당 `max_chars`로 자르고, 스킬이 꺼진 서버·실패한 스킬은 건너뛴다).
- **구현 결정 (2026-10-19, 12단계 Part 3)**: 스킬이 대화를 DM에서 열 수 있다(`NotifyService.open_dm_thread` — 대표 계정의 DM 채널을 열고 첫 말에 끝내기 버튼을 붙인다. 계정이 없거나 이미 이 스킬로 연 대화가 있으면 열지 않는다). 연 스킬은 `guidance`로 그 대화 안에서만 프롬프트 "맥락"에 들어가는 지침을 줄 수 있다. 전문(`ThreadTranscript`)에는 유니의 말도 `is_yuni`로 함께 남고 메모리 요약 대기 목록에는 플레이어 글만 간다. 모델이 대화를 끝내려면 `end_conversation`을 부르고(스레드 안에서만 보인다), 코어가 마무리 말을 보낸 뒤 `explicit`으로 닫는다. 끝내기 버튼(`core/thread_view.py`)은 판단 없이 바로 닫고 대화의 플레이어 본인만 누를 수 있다. 스레드(비공개 포럼식)를 만드는 길은 아직 없다 — DM만 연다.
- **구현 결정 (2026-10-19, 12단계 Part 1)**: 테이블은 `player_memory`(본문·`nickname`·`forgotten`·자동저장)와 `player_memory_pending`(플레이어당 한 줄, `due_at`은 epoch 초)이다(`migrations/core/015`). 요약 호출은 `YuniService.merge_memory`(`SUMMARY_MODEL`, 사용량 `kind="memory_summary"`)가 하고, 결과를 코드가 다시 검사한다(지운 항목 제거·중복 제거·1,500자 상한·호칭 다듬기). 요약 호출이 실패하면 5분 뒤 다시 하고 세 번 실패하면 버린다. 반영은 `YuniClient._poll_schedules`(60초)가 부르는 `MemoryService.flush_due`가 한다. 반응 이모지는 📝이다. 호칭은 `core/address.py`의 `AddressResolver`가 정하고, 게임 쪽 닉네임은 `bot.py`가 소스로 꽂는다(코어는 츄니즘을 모른다). 한마디 호출부에는 디스코드 메시지가 없으므로 호칭 3순위(서버 닉네임)는 멘션 응답에서만 쓴다. 표시물의 `private=True`는 멘션 응답에서 DM으로 보낸다(`core/mention.py`) — 기존 `ephemeral`을 멘션에서 DM으로 바꾸는 것은 아니다.

## 비용과 운영

10명 미만 규모에서 LLM 비용은 월 수 달러에서 수십 달러로 추정되고, 미니 PC에서 돌려도 포트를 열 필요가 없다.

**LLM 모델과 비용** ([Gemini API 가격표](https://ai.google.dev/gemini-api/docs/pricing), 2026-10-08 확인, 100만 토큰당 달러)

| 모델 | 입력 | 출력 | 용도 |
| --- | --- | --- | --- |
| Gemini 3.8 Flash | 0.75 (2026-12-31까지), 이후 1.50 | 3.75 (2026-12-31까지), 이후 7.50 | 멘션 에이전트 |
| Gemini 3.5 Flash-Lite | 0.30 | 2.50 | 메모리 요약, 유니의 한마디 같은 단순 작업 |
| Gemini 3.1 Flash-Lite | 0.25 | 1.50 | 더 싼 대안 |

- **추천 구성**: 에이전트는 3.8 Flash, 요약류는 3.5 Flash-Lite. 도구 고르기, 규칙 준수, 한국어 캐릭터 말투를 동시에 요구하는 쪽이 에이전트이기 때문이다.
- **Claude 선택지**: `LLM_PROVIDER=claude`면 `AGENT_MODEL`에 Claude 모델(예: `claude-haiku-5-5`)을 넣는다. 가격은 `core/llm_pricing.py`에 있고, 요금표에 없는 모델이면 월 상한 계산이 멈춘다. Claude 어댑터는 아직 프롬프트 캐시를 쓰지 않는다.
- **검증 방법**: 이 조합을 잰 공개 벤치마크는 찾지 못했다. 스킬들의 `examples`를 모아 두 모델에 똑같이 돌리고, 도구 선택 오류와 숫자 규칙 위반을 센다. Flash-Lite가 통과하면 에이전트도 Flash-Lite로 내린다.
- **Google 검색**: 유료 등급에서만 쓸 수 있다. 월 5,000회까지 무료(Gemini 3 계열 공용)이고 이후 1,000회당 14달러다. 이 규모에서는 무료 한도 안에 든다. 함수 호출과 검색을 한 요청에 함께 쓰는 기능은 Gemini 3 계열에서 지원된다([문서](https://ai.google.dev/gemini-api/docs/tool-combination)).
- **무료 등급을 쓰지 않는 이유**: 검색을 못 쓰고, 입력 내용이 구글 제품 개선에 쓰인다. 친구들의 대화와 메모리가 들어가므로 유료 등급을 쓴다.
- **쓰지 않는 모델**: Gemini 2.5 Flash와 2.5 Flash-Lite는 [종료 일정](https://ai.google.dev/gemini-api/docs/deprecations)에 2026-10-16 종료로 올라 있다. (2026-10-12 재확인: 2.5 계열의 종료일은 미정으로 바뀌었다 — 기존 사용자에게만 "추가 공지까지" 유지되는 상태이고 신규 지원 중단은 아니다. 3.8 Flash/3.5 Flash-Lite를 쓴다는 결론은 바뀌지 않는다.)
- **사고 토큰**: 출력 가격에 포함된다. 사고 수준을 낮게 설정한다.
- **응답 한 번의 비용**: 3.8 Flash가 1센트 안팎, 3.5 Flash-Lite가 0.4센트 안팎으로 추정한다. 입력 1만 토큰, 출력 400토큰을 가정한 캐싱 전 어림값이다.
- 규칙·말투 파일과 스킬 카드는 매번 같으므로 컨텍스트 캐싱을 쓴다. 카드 순서를 고정해 캐시가 깨지지 않게 한다.
- 가격과 모델은 자주 바뀐다. 구현 시점과 2027년 1월에 가격표를 다시 확인한다.

**구동 환경: 우분투 서버 미니 PC**

- **실행 방식**: Docker Compose. 이 저장소의 Dockerfile로 직접 빌드한다. Python 3.14 이미지를 써서 우분투의 기본 파이썬 버전에 묶이지 않는다.
- **아키텍처**: CPU가 라이젠 5이므로 x86-64다.
- **자동 시작**: 재시작 정책 `unless-stopped`와 부팅 시 Docker 시작. 기기가 켜지면 봇도 올라온다.
- **보존할 것**: DB가 든 `data` 폴더, 설정 파일, 토큰과 암호화 키가 든 `.env`. 셋 다 컨테이너 밖 볼륨에 둔다. `data/http_cache.sqlite`는 캐시라 지워도 되고 백업하지 않는다.
- **로그**: `core/log_setup.py`가 표준 출력(`docker logs`)과 `data/logs/yuni.log`(5MB씩 최대 6개 돌려 씀)에 같이 남긴다. `docker compose up --build` 등으로 컨테이너가 재생성되면 `docker logs`는 그 컨테이너와 함께 사라지지만, 로그 파일은 볼륨(`data/`) 안이라 남는다(2026-10-19 실기: 컨테이너 재생성 직후 원인 분석이 막혀 결정).
- **네트워크**: 디스코드와 외부 API로 나가는 연결만 쓴다. 포트 개방과 고정 IP가 필요 없다. 웹 로그인 서버는 두지 않는다.
- **디스코드 설정**: 멘션과 답장을 읽기 위해 메시지 내용 인텐트를 켠다.

**새벽 정지 시간에 맞춘 동작** (정지 시간대는 설정값 `QUIET_HOURS_START`/`QUIET_HOURS_END`, 기본 02시\~06시)

| 상황 | 처리 |
| --- | --- |
| 꺼지기 직전 | 종료 신호를 받으면 열린 대화 스레드를 중단으로 닫아(전문이 연 스킬과 메모리 대기 목록으로 간다) 대기 중인 메모리 요약을 마저 처리한 뒤 DB를 닫는다. 요약은 최대 20초까지만 기다리고, 못 끝낸 것은 대기 목록에 남아 다음 기동에서 이어진다. Compose의 종료 유예 시간을 넉넉히 둔다 |
| 꺼져 있는 동안 온 멘션 | 응답하지 않는다. 켜진 뒤 소급해 답하지도 않는다 |
| 켜진 직후 | `catch_up` 예약을 점검하고, 공지와 곡 목록을 한 번 확인한다 |
| 예약 작업 | 시각을 모두 정지 시간대 밖으로 잡는다 |
| 백업 | 켜진 직후 DB를 하루 한 번 복사하고 최근 14개를 남긴다. 암호화 키는 다른 곳에 따로 보관한다 |

- 세션의 날짜 경계인 새벽 4시가 정지 시간대 안에 있어, 꺼지기 전의 플레이는 전날 세션에 붙는다.
- 전원을 끄지 않고 절전으로 재우는 경우에도 같은 처리가 통한다. 깨어난 뒤 디스코드 연결이 다시 붙는지는 시험한다.
- 꺼지기 전과 켜진 뒤에 유니가 인사하는 기능은 두지 않는다. 매일 두 번 채널에 글이 올라가기 때문이다. 원하면 스킬로 더할 수 있다.

## 다른 게임으로의 확장 여지

지금은 츄니즘만 만든다. 마이마이나 아르케아 같은 다른 게임을 나중에 얹을 수 있도록 츄니즘 데이터와 코드를 최상위에 두지 않고 츄니즘이라는 이름 아래에 둔다. 확장 자체는 설계하지 않는다.

| 대상 | 규칙 |
| --- | --- |
| 서비스 | 게임 전용 서비스는 `services/chunithm/`에 둔다. 공통 서비스는 게임을 모른다 |
| 스킬 | manifest의 `game`으로 묶는다. 게임 전용 스킬 이름은 `chunithm-`으로 시작한다 |
| 테이블 | 게임에 딸린 테이블에는 `game` 열을 둔다 |
| 이벤트 | 이름 앞에 게임을 붙인다. 예: `chunithm.sync.completed` |
| 설정 파일 | 츄니즘 관련 설정은 `[chunithm]` 구획에 모은다 |
| 플레이어 메모리 | 게임별 구획을 둔다. 호칭 같은 공용 사실은 구획 밖에 둔다 |
| 슬래시 명령 | 지금은 게임 이름 없이 둔다. 게임이 늘면 그때 게임별 묶음으로 옮긴다 |

- **게임과 무관한 것**: 플레이어와 디스코드 계정, 태그, 메모리, 약속과 함께한 기록, 오락실 목록과 별칭, 예약과 이벤트 틀, 인격과 반응 단계의 구조.
- **하지 않는 것**: 여러 게임을 아우르는 공통 인터페이스나 추상 계층은 지금 만들지 않는다. 두 번째 게임이 실제로 정해졌을 때 그 게임에 맞춰 만든다.
- 유니는 츄니즘 캐릭터다. 다른 게임을 얹을 때 인격을 어떻게 할지는 그때 정한다.

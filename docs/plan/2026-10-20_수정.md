# 계획 수정 (2026-10-20)

`docs/plan.md` §4 작업 단계 중 2026-10-20에 계획 밖에서 더한 단계의 상세다. `plan.md`에는 단계마다 한 줄, 완료 표시, 이 파일의 절 번호만 둔다.

## 13. `chunithm-settings`

사용자 요청. 지금 계정의 인게임 설정(스피드·필드 월·판정 타이밍 A·B·가이드음) 조회·변경, 즐겨찾기 곡 조회·추가·삭제. `chunithm-arcade`의 `current_settings`를 이 스킬로 옮기고 표시 포맷 도우미를 서비스로 공유, `SongRecord`에 SEGA musicId(`id`)를 더해 즐겨찾기 id를 곡 이름으로 되찾는다. 상세는 `chunithm-settings.md` "구현 결정".

실기 미확인: 실제 계정으로 "내 지금 설정 보여줘"·"스피드 9.00으로 바꿔줘"가 CHUNITHM-NET에 실제로 반영되는지, 즐겨찾기 추가/삭제가 실제 인게임 화면에 반영되는지, 잘못된 값("스피드 100으로")에 도구가 거절하는지

## 14. `chunithm-folders`

사용자 요청. 채보를 모아 이름 붙인 폴더(난이도·상수·자유 조합)를 만들고, 채보를 하나씩 또는 조건(상수 범위·레벨·수록 버전) 일괄로 추가/삭제, 이름 변경, 메모. CHUNITHM-NET과 무관하게 이 봇 DB에만 저장. 조건 검색은 기존 `songdb.find_by_const`/`find_by_level`/`find_by_version`을 그대로 쓴다. 상세는 `chunithm-folders.md`.

실기 미확인: "15.0 상수 곡 모아서 폴더 만들어줘"에 유니가 이름을 스스로 지어 생성+일괄 추가를 이어 하는지, 대상이 많을 때 확인 버튼이 뜨는지, `/폴더` 슬래시 그룹의 하위 명령 등록

## 15. `yuni-lore`

사용자 요청. 유니·나비·Linked VERSE 설정집(`skills/yuni-lore/lore.md`)을 게이트 단위 구간으로 읽는 `read_lore` 도구. 결말 쪽 구간은 `spoiler_ok`가 있어야 나가고 지침으로도 먼저 묻게 한다. 새 category "유니 설정" 추가. 상세는 `yuni-lore.md`.

실기 미확인: 설정을 물으면 목록을 본 뒤 구간 하나만 읽고 짧게 답하는지, 결말을 물으면 스포일러 확인을 먼저 하는지, 묻지 않은 대화에서 안 펼치는지

## 16. 작업 표

사용자 요청. 여러 항목을 여러 스킬에 걸쳐 다룰 때 모델과 스킬이 **표 id만** 주고받게 한다. 모델이 점수 같은 원자료나 목표 id 같은 내부 값을 옮겨 적지 않게 하는 것이 목적이다. 기준 설계는 `docs/design/00-core.md` "작업 표"이고, 이 절은 그 설계를 **어떤 파일에서 무엇을 바꿔 구현하는지**를 적는다. 설계와 이 절이 다르면 설계가 맞다 — 이 절을 고친다.

### 16.0 용어

| 용어 | 뜻 |
| --- | --- |
| 표 | 코어가 메모리에 보관하는 작업 표. `t1`·`t2`처럼 id로 가리킨다. 한 번 만들면 바꾸지 않는다 |
| 행 | 표의 한 줄. 항목 하나(채보 하나, 목표 하나, 메모 하나…) |
| 가리키는 것 | 행마다 정확히 하나. 그 행 자체가 무엇인지(종류 + 키). 예: 종류 `chunithm-goals.goal`, 키 `a2`(목표 id). 키는 모델에게 보이지 않는다 |
| 칸 | 행의 값 하나. 칸마다 **원래 값**(거르기·정렬용)과 **보일 글자**(출력용)를 둘 다 가진다 |
| 공통 칸 | 여러 스킬이 알아봐야 하는 칸. 이름을 `services/chunithm/table_columns.py`에 상수로 정한다(16.2 참고) |
| 채보 행 | 곡 칸과 난이도 칸이 모두 차 있는 행 |
| 곡 단위 행 | 곡 칸은 차 있고 난이도 칸이 비어 있는 행(난이도 None) |
| 필요한 것 | 표를 받는 도구가 선언하는 조건. 가리키는 것의 종류, 또는 차 있어야 하는 칸 |
| 빼기 | 필요한 것이 없는 행을 그 도구의 입력에서 빼는 것. 뺀 수는 결과 표의 `steps`에 적는다 |

### 16.0.1 진행 순서

- Part 0은 다른 파트와 무관하게 언제든 할 수 있다.
- Part 1 → Part 2 순서는 고정이다. Part 3·4·5는 Part 2가 끝난 뒤 아무 순서로 해도 된다.
- Part 6은 `00-core.md` "작업 표 — 결정 대기" 4·5번이 정해지기 전에는 시작하지 않는다.
- 파트 하나가 작업 단위 하나다. 시작 전에 사용자에게 무엇을 할지 짧게 말하고 승인받는다.

### Part 0: 동기화 때 플레이어 레벨·캐릭터 그림 주소 저장

지금 동기화는 프로필 페이지를 이미 읽는다(`ChunithmNetService`가 만드는 `SyncFetch.profile`, chuni-penguin `Profile`). 그 안의 레벨·환생 별·캐릭터 그림 주소·프레임 주소를 버리고 있다. 저장만 더한다. 추가 접속은 없다.

- **마이그레이션** `migrations/core/018_records_profile.sql`: 새 테이블 `records_profile`
  - `player_id TEXT NOT NULL`, `game TEXT NOT NULL DEFAULT 'chunithm'`, `level INTEGER`, `reincarnation_stars INTEGER`, `character_image_url TEXT`, `character_frame_url TEXT`, `updated_at TEXT NOT NULL`, `PRIMARY KEY (player_id, game)`
  - 값이 없으면 NULL. 플레이어당 최신 한 줄만 둔다(이력은 남기지 않는다).
- **`services/chunithm/records.py`**
  - `_save_sync_locked`에서 `fetch.profile`의 `level`·`reincarnation_stars`·`profile_picture`·`profile_picture_frame`을 `records_profile`에 덮어쓴다(같은 트랜잭션).
  - 읽기 메서드 `player_profile(player_id) -> PlayerProfile | None` 추가. `PlayerProfile`은 위 네 값과 `updated_at`을 가진 frozen dataclass.
- **계정 연결로 플레이어를 합칠 때**: `records_profile`은 `player_id` 열이 있어 코어의 플레이어 데이터 정리 대상에 자동으로 들어가는지 확인한다(`docs/design/00-core.md` "데이터와 설정").
- **하지 않는 것**: 그림 파일을 받아 저장하는 것(결정 대기 7). 펭귄 아바타 부품(`user_avatar`) 저장.
- **시험**: 동기화 저장 후 `player_profile`이 네 값을 돌려주는지, 다시 동기화하면 덮어쓰는지, 프로필에 값이 없으면 NULL인지(`tests/services/chunithm/test_records.py`).
- **문서**: `docs/design/skills/chunithm-sync.md`에 저장하는 값 추가.

### Part 1: 코어

새 파일 `core/tables.py`에 표 구조·보관소·거르기 엔진을 두고, 나머지는 기존 파일을 고친다.

**1-1. 표 구조** (`core/tables.py`)
- `WorkTable`(frozen): `id`, `columns`, `groups`, `summary`, `steps`, `subject`(플레이어 id 또는 None), `unit`(표지의 개수 단위, 예 "채보")
- `Column`: `name`(공통 칸이면 그 상수), `label`(보이는 이름), `value_type`(`text`·`number`·`ScoreRef`·`RankRef`·`LampRef`·`DifficultyRef`), `slash_only`(슬래시 출력에서만 보이는 칸 — 지금 `slash_content`로 id를 보여 주던 도구들이 쓴다)
- `Cell`: `raw`(원래 값, 없으면 None), `text`(보일 글자)
- `Row`: `ref`(`RowRef(kind, key)`), `cells: dict[칸 이름, Cell]`
- `Group`: `title`(이름 없는 묶음이면 None), `summary`(묶음 요약, 없으면 빈 dict), `rows`
- 스킬이 표를 만드는 도우미: `TableBuilder` — 칸 정의, 행 추가, 묶음 추가, 요약·steps·subject·unit 지정 후 `build()`. id는 비워 두고 코어가 보관할 때 붙인다.

**1-2. 보관소** (`core/tables.py`의 `TableStore`)
- 메모리 dict. 키는 (플레이어 id, 채널 id). 재시작하면 사라진다.
- `put(table) -> id`(그 플레이어+채널에서 `t1`부터 늘어나는 번호), `get(player, channel, id)`, `bind(id, message_id)`(출력한 표를 유니 답장 메시지에 묶기), `retain_only(player, channel, alive_message_ids)`(맥락 안 메시지에 묶인 표만 남기고 지움), `expire(now)`(만든 지 24시간 지난 표 삭제).
- `expire`는 `core/bot.py`의 60초 폴링 루프(`_poll_schedules`와 같은 루프)에서 부른다.
- **옛 값 표시** (설계 "찍어 둔 값"): `mark_stale(subject_player_id)` — 모든 채널에서 `subject`가 그 플레이어인 표의 id를 "옛 값" 집합에 넣는다. `is_stale(player, channel, id)`로 확인한다. 표 객체는 바꾸지 않는다. 옛 값 표로 `table_query`를 해서 만든 표도 보관할 때 "옛 값" 집합에 넣는다.
- 스킬이 보관소의 일반 기능을 쓸 수 있게 `ToolContext.tables`(이 `TableStore`)를 연다. 지금 스킬이 쓰는 것은 `mark_stale` 하나뿐이다.
- `ToolContext`에 `channel_id: str | None`을 더한다. 멘션 경로(`core/mention.py`)는 트리거 메시지의 채널 id를, 대화 스레드는 스레드 id를 넣는다. 슬래시는 표를 보관하지 않으므로 None이다.

**1-3. 도구 결과와 인자** (`core/tool_types.py`, `core/executor.py`, `core/schema.py`)
- `ToolResult.table: WorkTable | None` 추가. 표를 돌려주는 도구는 `display`를 비운다.
- 표준 인자 타입 `TableRef` 추가(`STANDARD_REF_TYPES`에 넣는다). 모델은 `"t3"` 또는 번호를 붙인 `"t3:2,3"`을 넘긴다(설계 "표 인자에 번호 붙이기"). 문법은 정확히 `t<숫자>` 또는 `t<숫자>:<숫자>[,<숫자>…]`이고, 그 밖의 모양(공백 제외)은 에러 "표 id 모양이 틀렸다".
- 필요한 것 선언: `Annotated[TableRef, TableNeeds(ref_kind=..., columns=[...], nonempty=[...], single=False)]`. `ref_kind`(가리키는 것의 종류)나 `columns`(있어야 하는 칸)·`nonempty`(차 있어야 하는 칸) 중 쓰는 것만 준다. `single=True`면 남은 행이 정확히 하나여야 한다(항목 하나만 다루는 도구, 설계 "슬래시와 같이 쓰기").
- 실행기(`core/executor.py`)가 `TableRef` 인자를 해석할 때 할 일, 순서대로:
  1. 문자열을 표 id와 번호 목록으로 나눈다.
  2. 보관소에서 (요청 플레이어, 채널, id)로 찾는다. 없으면 에러 "그 표 없음(지난 표이거나 다른 채널의 표)".
  3. 도구가 `mutates=True`이고 그 표가 "옛 값"이면 도구를 부르지 않고 에러 "표가 동기화 전 값이라 다시 만들어야 한다". 바꾸지 않는 도구는 옛 값 표도 받는다(결과 표도 옛 값이 된다).
  4. 번호가 있으면 `table_query`의 `rows`와 같은 함수로 그 행만 고른다. 같은 규칙: 이번 턴에 만든 표(`turn_table_ids`)면 에러 "번호는 사람이 본 표에만 쓴다", 없는 번호면 에러 "그 표는 N행까지 있다". `steps`에 "2·3번"을 적는다.
  5. 행마다 필요한 것을 확인하고 없는 행을 뺀 **새 입력 표**를 만든다. `steps`에 "곡 없는 행 N개 뺌"처럼 적는다.
  6. 남은 행이 0개면 도구를 부르지 않고 에러 "대상 행이 없다(전부 N개 뺌)". `single=True`인데 2개 이상이면 에러 "한 행만 골라야 한다(지금 N개)".
  7. 도구 함수에는 `WorkTable` 객체를 넘긴다.

**1-4. 에이전트 처리** (`core/agent.py`)
- 도구가 표를 돌려주면: 보관소에 넣고 id를 받는다 → 모델에게 주는 함수 응답에는 아래 **표 요약**만 넣는다 → 이 턴의 "마지막 표"를 그 id로 바꾼다.
- 표 요약 모양(모델이 보는 전부):
  ```
  {"table": "t3", "rows": 9, "unit": "채보",
   "columns": ["곡", "난이도", "상수", "점수"],
   "groups": [{"title": "15.5", "rows": 4}, ...],
   "steps": ["15.0 상수 MAS", "내 점수", "점수<SSS"],
   "summary": {"레이팅": "16.98"}}
  ```
  `slash_only` 칸은 `columns`에 넣지 않는다. 가리키는 것의 키와 `subject`는 넣지 않는다. 옛 값 표면 `"stale": true`를 더한다.
- 숫자 대조(`collected_data`)에는 모델이 받은 것만 넣는다: 표 요약, `table_peek` 결과. 출력에만 쓰인 행 값은 넣지 않는다.
- `AgentTurnResult`에 `last_table_id`, `drawn_table_ids`(그림 표로 이미 그린 표, 1-7), `turn_table_ids`(이번 턴에 만든 표 전부)를 더한다. `table_query`·`table_peek`은 `turn_table_ids`로 번호 사용을 막는다(1-5).

**1-5. 코어 내장 도구** (`core/agent.py`의 `_invoke`, `list_capabilities`와 같은 방식으로 등록. 슬래시 없음)
- `table_query(table, rows=None, exclude_rows=None, where=[], sort=None, descending=False, limit=None, group_by=None)` → 새 표
  - `rows`·`exclude_rows` (설계 "번호로 행 고르기"): 정수 목록. 번호는 그 표를 출력할 때 찍은 번호, 곧 묶음 순서대로 행을 늘어놓았을 때 1부터 센 위치다(`core/tables.py`의 `row_at(table, number)` 하나로 계산해 출력·텍스트 파일·그림 표·고르기가 모두 같은 함수를 쓴다). `rows`가 있으면 그 행만, `exclude_rows`가 있으면 그 행을 빼고 남긴다. 둘 다 `where`보다 먼저 적용한다. 없는 번호가 하나라도 있으면 에러 "그 표는 N행까지 있다".
  - 이번 턴에 만든 표(1-4의 `turn_table_ids`)에 `rows`·`exclude_rows`가 오면 에러 "번호는 사람이 본 표에만 쓴다". 이전 턴에서 살아남은 표는 모두 출력된 표라 허용한다.
  - 번호로 고른 뒤 데이터를 바꾸려면 모델은 `table_query(t3, rows=[2,3])`로 새 표를 만들고, 그 새 표를 바꾸는 도구에 넘긴다(새 표는 이번 턴 표지만 번호를 쓰지 않으므로 막히지 않는다).
  - `where` 항목: `{"column": 칸 보이는 이름, "op": "==" | "!=" | "<" | "<=" | ">" | ">=" | "contains", "value": 문자열}`. 여러 개면 AND.
  - `value`는 그 칸의 `value_type`으로 해석한다. `number`는 숫자로 읽고, `ScoreRef`·`RankRef`·`LampRef`·`DifficultyRef`는 그 해석기로 바꾼다("SSS" → 1,007,500). 해석 실패는 에러.
  - 값이 없는 행(`raw` None)은 **모든 조건을 통과**한다(설계의 임시 결정). 정렬에서는 방향과 무관하게 맨 뒤.
  - `sort`는 묶음 안에서만 정렬한다. 같은 값이면 원래 순서를 지킨다.
  - `limit`은 묶음마다 앞에서 N개.
  - `group_by`: 칸 이름이면 그 칸 값으로 다시 묶는다(묶음 순서는 원래 값 내림차순, 표지 이름은 보일 글자). 빈 문자열이면 묶음을 풀어 하나로. 주지 않으면 원래 묶음 유지.
  - 결과 표는 `summary`와 묶음 요약을 버리고(다시 묶지 않았으면 표지 이름은 유지), `steps`에 조건을 사람이 읽는 말로 덧붙인다. 비어 버린 묶음은 뺀다.
- `table_peek(table, rows=None, where=[], sort=None, descending=False, limit=10)` → 표를 만들지 않고 고른 행의 **원래 값**을 `data`로 돌려준다. `limit` 최대 20. 출력은 없다. `rows` 규칙은 `table_query`와 같다("3번 점수 얼마야?" → `table_peek(t3, rows=[3])`). 돌려주는 행마다 번호를 함께 넣는다.
- 두 도구는 같은 엔진(`core/tables.py`의 `select_rows`)을 쓴다.

**1-6. 글자 출력** (`core/tables.py`의 `render_text`, `core/response_assembly.py`)
- 턴 끝에 `last_table_id`의 표 하나만 그려 required·omittable 표시물로 붙인다. `drawn_table_ids`에 있으면 그리지 않는다. `[[no_table]]`이면 붙이지 않는다.
- 모양: 첫 줄들에 `steps`(→로 잇기)와 `summary`, 그다음 묶음마다 표지 줄 `── {title} · {행 수}{unit} ──`(묶음 요약이 있으면 뒤에 붙임), 그 아래 행마다 `{번호}. {칸 보일 글자들을 두 칸 띄어 잇기}`. 번호는 표 전체에서 1부터 이어진다. 이름 없는 묶음 하나뿐이면 표지 줄을 생략한다. 옛 값 표면 머리말 첫 줄에 `(동기화 전 값)`을 찍는다.
- 행이 10개를 넘으면(`TABLE_FILE_ROWS = 10`) 머리말만 메시지에 두고, 묶음과 행 전체는 `.txt` 파일(UTF-8)로 첨부한다. 파일 이름은 `steps` 첫 항목 기반(예 `15.0상수MAS.txt`, 안 되면 `table.txt`).
- `slash_only` 칸은 슬래시 출력에서만 그린다.

**1-7. 첨부 파일과 그림 표 표시** (`core/tool_types.py`, `core/bot.py`, `core/slash.py`)
- `Display.files: list[DisplayFile]`(이름, 바이트) 추가. 멘션 `_send`(`core/bot.py`)와 슬래시 `respond`(`core/slash.py`)가 `discord.File`로 실어 보낸다. 본문을 2000자로 나눌 때 파일은 첫 조각에 붙인다.
- `ToolResult.drew_table: str | None` 추가. 그림 표 도구가 그린 표 id를 넣으면 에이전트가 `drawn_table_ids`에 넣는다.
- 슬래시 경로가 `ToolResult.table`을 받으면 보관하지 않고 바로 `render_text`로 그려 보낸다(같은 파일 규칙).

**1-8. 수명 연결** (`core/mention.py`)
- 응답을 보낸 뒤 이 턴의 마지막 표를 유니 답장 메시지 id(나눠 보냈으면 첫 조각)에 `bind`한다. 마지막 표가 아닌 이 턴의 표는 지운다.
- 멘션을 받을 때마다 `build_conversation_context`가 고른 맥락 메시지 id로 `retain_only`를 부르고, 남은 표마다 프롬프트 조각을 넣는다: `[살아 있는 표] t3 — 15.0 상수 MAS → 내 점수 → 점수<SSS (9채보, 칸: 곡·난이도·상수·점수)`. 옛 값 표면 id 뒤에 `(동기화 전 값)`을 붙인다.
- 번호 기준 줄도 넣는다 (설계 "번호로 행 고르기"):
  - 트리거 메시지가 유니 메시지에 단 답장이고 그 메시지에 묶인 표가 살아 있으면 `답장한 메시지의 표: t3`.
  - 살아 있는 표 중 가장 최근에 묶인 것은 `마지막으로 보여 준 표: t5`.
  - 보관소에 `table_for_message(player, channel, message_id) -> id | None`과 `last_bound(player, channel) -> id | None`을 더한다.
- 대화 스레드 안에서는 스레드가 닫힐 때까지 표를 지우지 않는다(닫힐 때 그 스레드 채널의 표를 모두 지운다).

**1-9. 프롬프트** (`prompts/rules.md`)
- 표 id를 받으면 행을 다시 나열하지 않는다. 표의 개수·요약만 말한다.
- 이어지는 요청("그중에…")은 프롬프트의 살아 있는 표를 `table_query`로 다룬다. 원래 도구를 다시 부르지 않는다.
- 행 값을 말해야 할 때만 `table_peek`을 부른다.
- `(동기화 전 값)` 표는 이어지는 요청에 쓰지 않고, 그 표를 만든 원래 도구를 다시 부른다.
- 사람이 "2번", "1번 빼고", "3번부터 5번"처럼 번호로 말하면 행 값을 읽어 조건을 만들지 말고 `rows`·`exclude_rows`에 번호를 그대로 넣는다. 그 행을 바로 다른 도구에 넘길 때는 `table_query`를 거치지 않고 표 인자에 `"t3:2,3"`처럼 붙인다. 어느 표의 번호인지는 `답장한 메시지의 표`가 있으면 그 표, 없으면 `마지막으로 보여 준 표`다.

**1-10. 시험** (`tests/core/test_tables.py` 새로, 기존 `test_agent.py`·`test_response_assembly.py`·`test_mention.py`·`test_slash.py`에 더하기)
- 표를 바꾸지 않는지, id가 플레이어+채널마다 따로 늘어나는지, 다른 플레이어·채널에서 못 찾는지
- 필요한 것이 없는 행을 빼고 `steps`에 적는지, 0개면 도구를 부르지 않는지
- `table_query`의 비교·`ScoreRef` 해석·값 없는 행 통과·묶음 안 정렬·묶음마다 limit·다시 묶기·풀기
- 모델 요약에 키·`subject`·`slash_only` 칸이 없는지, 숫자 대조가 요약만 쓰는지
- 마지막 표만 그리는지, 그림으로 그린 표는 글자로 안 그리는지, 11행부터 파일로 가는지
- 맥락에서 밀려난 표와 24시간 지난 표가 지워지는지
- 번호: 묶인 표에서 번호가 묶음을 넘어 이어지는지, 출력·텍스트 파일·`rows`가 같은 행을 가리키는지, `exclude_rows`, 없는 번호 에러, 이번 턴에 만든 표에 번호를 쓰면 거절하는지, 프롬프트 조각의 답장한 메시지의 표·마지막으로 보여 준 표
- `"t3:2,3"`: `rows=[2,3]`과 같은 행을 넘기는지, 틀린 모양 에러, 번호 규칙이 똑같이 걸리는지, 번호로 고른 뒤 빼기를 하는지, `single=True` 도구에 2행이 오면 거절하는지
- `mark_stale`이 그 플레이어가 `subject`인 표에만 붙는지(다른 플레이어 표·`subject` 없는 표는 그대로), 옛 값 표에서 거른 표도 옛 값인지, `mutates=True` 도구가 옛 값 표를 거절하는지, 바꾸지 않는 도구는 받는지, 요약·프롬프트 조각·출력 머리말에 옛 값이 보이는지

- 항목 하나를 보는 도구: `chunithm-report.profile`·`record`, `chunithm-song.info`·`chart`·`chart_link`, `chunithm-goals.progress`, `chunithm-border.lookup`·`remaining`, `chunithm-account.status`, `chunithm-settings.current_settings`, `chunithm-arcade.get_settings`, `chunithm-updates.next`, `chunithm-terms.explain`, `chunithm-notes.get_note`.
- `chunithm-session.get_session`: 세션 하나의 보고서이고, 다른 스킬이 이벤트로 붙이는 조각(오락실 설정·후기 등)이 섞여 있어 한 표로 담을 수 없다.
- `admin.usage`·`admin.skills`: 관리자 전용 비공개(ephemeral) 응답이라, 표를 채널에 출력하고 보관하는 규칙과 맞지 않는다.

### Part 6: id 입구 나누기와 표로 데이터 바꾸기 (결정 대기)

`00-core.md` "작업 표 — 결정 대기" 4·5번(전용 표시물 모양, 범위와 순서)이 정해진 뒤에 시작한다. **아직 구현하지 않는다.** 아래 6-1은 결정 대기 3번(슬래시와 같이 쓰기)이 정해져서 구체적으로 적었다.

**6-1. id를 받는 도구의 입구 나누기** (설계 "슬래시와 같이 쓰기")

각 도구는 (가) 지금 함수를 `@slash_only`로 바꿔 슬래시 이름·id 인자를 그대로 두고, (나) 슬래시 없는 모델용 새 도구를 만들고, (다) 실제 일은 스킬 안의 내부 함수 하나로 옮겨 둘이 같이 부른다. `SKILL.md` 지침에서 id 언급을 지우고 새 도구를 쓰게 한다.

| 지금 도구(슬래시) | 받는 id | 모델용 새 도구 | 표에서 필요한 것 | 비고 |
| --- | --- | --- | --- | --- |
| `chunithm-goals.delete`(`/목표 삭제`) | `goal_ids`(쉼표) | `delete_goals(table)` | `chunithm-goals.goal` | `mutates`, `confirm="bulk"` |
| `chunithm-goals.update`(`/목표 수정`) | `goal_id` | `update_goal(table, …지금과 같은 수정 인자)` | `chunithm-goals.goal`, `single=True` | `mutates` |
| `chunithm-goals.progress`(`/목표 진행`) | `goal_id` | `goal_progress(table)` | `chunithm-goals.goal`, `single=True` | 바꾸지 않음. 지금처럼 항목 하나 보기 표시물 |
| `chunithm-goals.todo_done`(`/투두 완료`) | `goal_id` | `complete_todos(table)` | `chunithm-goals.goal` + 유형 칸 "곡" | `mutates`, 2개 이상이면 `confirm="bulk"` |
| `yuni-bond.promise_close`(슬래시 없음, 모델 전용) | `promise_id` | `close_promises(table, kept: bool = True)` | `yuni-bond.promise` | 지금 도구는 모델 전용이라 슬래시 입구가 필요 없다 — 지금 도구를 없애고 새 도구로 바꾼다 |

- 그대로 두는 것: `chunithm-terms.review`(admin, `proposal_id`) — id가 표가 아니라 보고 채널 메시지에서 오는 관리 작업이다. 이름·곡·폴더 이름처럼 사람이 쓰는 말을 받는 도구(`chunithm-notes.delete`, 폴더 도구들, `memory.forget`)는 id가 아니므로 나누지 않는다.
- 예: "2번 목표 지워줘"(답장한 메시지의 표 `t3`) → `delete_goals("t3:2")` 한 번. "크로노 목표 지워줘"(표 없음) → `list_goals` → `delete_goals`에 넘기기 전 `table_query(where 곡=크로노)` → 3번.

**6-2. 표로 데이터를 바꾸는 새 도구** (후보 — 결정 대기 4·5 뒤 확정)

6-1·6-2에서 데이터를 바꾸는 모든 도구가 지킬 규칙(정해짐 — 설계 "찍어 둔 값" 2·3번):
- "옛 값" 표는 실행기가 막는다(Part 1-3에서 구현). 도구가 따로 검사하지 않는다.
- 도구는 실행 직전에 행마다 가리키는 것의 키로 지금 DB를 다시 읽는다. 이미 없어진 항목과 이미 원하는 상태인 항목(이미 완료된 목표, 이미 폴더에 있는 채보 등)은 바꿀 대상에서 뺀다.
- `confirm="bulk"`의 미리보기(`dry_run=True` 결과)는 다시 읽은 뒤의 **실제로 바뀔 개수**를 `count`로 돌려주고, 뺀 것이 있으면 "N개는 이미 없음/이미 처리됨"을 함께 보여 준다.
- 실행 결과 `data`와 유니의 말도 실제로 바뀐 개수만 말한다.

- `chunithm-folders`: 이미 있는 폴더에 표의 채보를 일괄 추가/삭제. 지금의 `add_by_condition`/`remove_by_condition`을 없앨지.
- `chunithm-goals`: 표의 채보를 To-Do로 일괄 추가(`todo_bulk`를 대신할지). 목표 삭제·완료는 6-1에 있다.
- `chunithm-notes`: 표의 메모 삭제.
- `chunithm-settings`: 표의 곡을 즐겨찾기에 일괄 추가(곡마다 CHUNITHM-NET 호출, `cost="network"`).

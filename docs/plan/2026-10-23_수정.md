# 계획 수정 (2026-10-23)

`docs/plan.md` §4 작업 단계 중 2026-10-23에 계획 밖에서 더한 단계의 상세다. `plan.md`에는 단계마다 한 줄, 완료 표시, 이 파일의 절 번호만 둔다.

## 17. maimai DX 국제판 확장

사용자 요청. 두 번째 게임으로 국제판 maimai DX를 더한다. 새 스킬 묶음을 따로 만들지 않고, **기존 서비스·스킬에 게임 매개변수를 두고 게임마다 DB 대상과 일부 로직만 갈아 끼운다.**

`plan.md` §1 "제외"의 "다른 게임용 공통 추상 계층(두 번째 게임이 실제로 정해질 때 만든다)"은 이 단계로 조건이 찼다 — 그 줄을 지우고 범위 표에 이 단계를 넣는다.

### 17.1 원칙

- **게임은 문자열 매개변수 `game`(`"chunithm"`·`"maimai"`)이다.** 코어는 게임 이름만 들고 다니고 게임 규칙을 모른다.
- **게임마다 다른 것은 "게임 프로필" 한 곳에 모은다**: 점수 형식, 랭크·램프 표, 레이팅 공식과 프레임 크기, 채보 키 모양, 곡 DB 소스, NET 어댑터. 서비스는 프로필을 받아 동작하고, `if game == …` 분기를 여기저기 뿌리지 않는다(설계 원칙 3).
- **츄니즘 동작은 바뀌지 않는다.** 공통화 파트(17.3)는 리팩터이고, 기존 시험 전부가 그대로 통과해야 한다(스킬 이름 바꾸기에 따른 시험 수정은 예외).
- **어느 게임인지는 이 순서로 코드가 정한다**: ① 사용자가 말한 게임(모델이 도구 인자 `game`에 넣는다) → ② 플레이어별 "주 게임" 설정 → ③ 기본 게임(츄니즘). 모델은 사용자가 게임을 말했을 때만 `game`을 넣는다.

### 17.2.1 maimai 난이도

지금 난이도 순서·이름은 츄니즘 값으로 고정돼 있다(`services/chunithm/songdb.py`의 `_CHART_ORDER`·`_DIFFICULTY_RANGE_ORDER`·긴 이름 표, `table_columns.py`의 `DIFFICULTY_ORDER`). 이것들을 게임 프로필로 옮기고 maimai 값을 정한다.

| 짧은 코드 | 긴 이름 | 순서 | 비고 |
| --- | --- | --- | --- |
| `BAS` | BASIC | 1 | |
| `ADV` | ADVANCED | 2 | |
| `EXP` | EXPERT | 3 | |
| `MAS` | MASTER | 4 | |
| `REM` | Re:MASTER | 5 | **일부 채보에만 있다**(otoge-db `lev_remas`·`dx_lev_remas`가 빈 곡은 없음). 표시는 `Re:MAS` |
| `UTA` | 宴(UTAGE) | — | **츄니즘 WE와 같은 취급**(사용자 결정 2026-10-23): 상수 없는 채보로 기록·검색은 하고, 레이팅·정렬 순서·난이도 범위에서 빠진다 |

- 정렬 순서와 난이도 범위(`min_difficulty`·`max_difficulty`): BAS < ADV < EXP < MAS < REM. 기본 정렬(내림차순)이면 REM이 맨 앞 — 츄니즘의 ULT 자리와 같다.
- 별칭(`terms` maimai 사전): Re:MASTER·Re:MAS·리마스터·리마스·리마·흰보(흰 채보) → `REM`. 보라보 → `MAS`. 츄니즘 사전과 섞이지 않는다(같은 "마스"라도 게임별 사전에서 찾는다).
- NET 파서: maimai DX NET은 난이도를 0~4 번호(`diff=4`가 Re:MASTER)로 다룬다(maimai.py `get_level_index`). 이 번호↔코드 표도 프로필에 둔다.

### 17.3 Part 1: 게임 공통화와 스킬 이름 바꾸기

**서비스** (츄니즘 동작 변화 없음)

- `services/chunithm/` → `services/game/`(공통) + 게임별 모듈. 공통: `records`·`records_calc`의 틀, `chart_ref`, `table_columns`, `image_cache`, `rating_format`. 게임별: NET 어댑터, 곡 DB 소스, 레이팅 공식, 용어 사전.
- 게임 프로필 자료형과 등록부(이 파트에선 `chunithm` 하나만 등록).
- `RecordsService`·`SongDbService`·`TermsService`·NET 서비스가 `game`을 받는다. 지금 테이블의 `game DEFAULT 'chunithm'` 칸을 실제로 쓴다(대부분 테이블에 이미 있다).
- 게임 고르기(17.1 순서)는 한 함수로 두고 도구 실행기·슬래시 경로가 같이 쓴다.
- 코어 정리: `core/bot.py`의 `services.chunithm.*` 직접 import를 게임 등록부 한 곳으로, `core/registry.py` 서비스 이름, `core/permissions.py` 상태 태그(`chunithm-linked` → `sega-linked`, `chunithm-synced` → 게임별 `<game>-synced`), 이벤트 `chunithm.login.expired` → `sega.login.expired`.
- SKILL.md `game:` 한 값 → `games:` 목록(예: `[chunithm, maimai]`). `core/manifest.py` 검사도 같이.
- 태그: 두 게임을 다루는 스킬은 `tags_any: [chunithm-synced, maimai-synced]`처럼 받아 카드를 보이고, 고른 게임의 기록이 없으면 도구가 "그 게임은 아직 동기화 전"이라고 돌려준다.
- 이벤트: 이름 규칙 `게임.영역.사건`을 그대로 쓴다. `sync`는 고른 게임에 따라 `chunithm.sync.completed`·`maimai.sync.completed`를 내고, 두 게임을 다루는 스킬은 둘 다 받는다. 츄니즘 전용 스킬(`chunithm-updates`·`chunithm-arcade`)은 지금처럼 `chunithm.*`만 받으므로 손댈 것이 없다. 츄니즘 이벤트 이름은 바꾸지 않는다(`chunithm.login.expired`만 게임 공통이라 `sega.login.expired`로).
- 슬래시 명령: 게임을 다루는 명령(`/동기화`·`/베스트` 등)에 선택 인자 `게임`을 더한다. 없으면 17.1의 ② → ③. 게임별 명령 묶음은 만들지 않는다(사용자 결정 2026-10-23).

### 17.4 Part 2: DB 마이그레이션

새 마이그레이션만 더한다(적용된 SQL은 고치지 않는다).

- `records_pb`: 새 칸 `chart_type TEXT NOT NULL DEFAULT ''`(츄니즘은 `''`, maimai는 `STD`·`DX`)을 기본 키 `(player_id, game, song_title, chart_type, difficulty)`에 넣는다 — 테이블 재생성 + 복사(사용자 결정 2026-10-23). `dx_score INTEGER` 칸.
- 채보를 키로 드는 스킬 테이블에도 채보 종류: `folders_charts`·`notes_notes`는 기본 키에 `chart_type`(재생성 + 복사), `goals_goals.target_ref`(JSON)는 키 `chart_type`을 더한다(마이그레이션 없음, 없으면 `''`). 게임 칸은 이미 다 있다(`folders_folders`·`notes_notes`·`goals_goals`·`session_reports`·`records_*`).
- 세션: 같은 날 두 게임을 하면 세션·리포트가 게임별로 따로 생긴다(`records_sessions`의 `UNIQUE (player_id, game, play_date)` 그대로).
- 곡 별칭 `songdb_aliases`: 게임 칸(같은 별칭이 두 게임에서 다른 곡일 수 있다).
- `yuni_bond_milestones`: `chart_type` 칸을 더하고 UNIQUE에 넣는다(2026-10-23 사용자 결정 — 게임별 이정표 자체는 이번 단계 밖이지만 STD/DX 충돌을 미리 막는다).
- 쿠키 테이블: `chunithm_net_cookies`(PK `player_id`)를 그대로 쓰고 이름만 `sega_cookies`로 바꾼다(`clal`은 게임 공통).
- 플레이어 "주 게임" 설정(없으면 기본 게임).

### 17.5 Part 3: aime 인증 공통화와 maimai DX NET 어댑터

- **0단계 실측(블로커)**: SEGA 사이트가 복구된 뒤(2026-10-21 23:00부터 PHP 보안 문제로 접속 불가) 실제 계정으로 maimai 국제판 `site_id`·리다이렉트, 같은 `clal`로 들어가는지, 기록·최근·프로필 페이지 HTML을 확인한다. HTML 표본은 개인 정보를 지우고 `docs/reference/maimai-net/`에 둔다.
- `services/common/aime_auth.py`: chuni_penguin의 `ChunithmNetAuth` 흐름(쿠키 자동 로그인 → 실패 시 sid/비밀번호 → 액세스 코드 없음 감지)을 `site_id`·`redirect_url` 매개변수로 다시 짠다(`third_party/`는 고치지 않으므로 새로 쓴다). 츄니즘 쪽은 처음엔 기존 경로를 그대로 두고, 이 함수로 바꿀지는 나중에 따로 정한다.
- maimai 파서: maimai.py `page_parser.py`를 selectolax로 옮겨 적는다. 시험은 0단계 HTML 표본으로.
- maimai 어댑터: 프로필, 난이도별 전 기록, 최근 플레이. 지금 `ChunithmNetAdapterLike` 프로토콜 모양에 맞춘다.
- 오류: 로그인 만료, 점검, "이 계정에 maimai 플레이 기록 없음"을 `UserFacingError`로.
- 비밀값 규칙 그대로: `clal` 복호화는 `secrets`·NET 서비스 안에서만.

### 17.7 Part 5: 기록·레이팅·동기화

구현됨(2026-10-24, NET 없이 가능한 범위):

- 동기화 입력은 게임 중립 `SyncSnapshot`(`services/game/sync_types.py`): 프로필, 베스트/신곡 목록(선택), 최근 플레이, 전체 기록. 어댑터가 자기 응답을 이 모양으로 바꿔 넘긴다(CHUNITHM: `services/chunithm/sync_snapshot.py`, `ChunithmNetService.fetch_snapshot`). 동기화 스킬은 `fetch_snapshot`을 부른다. maimai NET이 베스트 목록을 주면(사용자 추정 2026-10-24, 미확인) 그대로 `best`·`new`에 담고, 안 주면 `None`으로 두면 서비스가 전체 기록과 신곡 판정으로 프레임을 짠다.
- 채보 키는 `(제목, 채보 종류, 난이도)`. `ChartUpdate`·`UnchangedPlay`·`FrameExit`·`LampChange`·`PbRow`·`CandidateHit`에 `chart_type`(기본 `""`)을 더했고 `PbRow`에 `dx_score`. `pb_row`·`best_score`는 `chart_type=""` 선택 인자, `pb_rows_for`는 `(제목, 난이도)`와 `(제목, 종류, 난이도)` 키를 모두 받아 넘긴 모양 그대로 돌려준다. 옛 세션 상태 JSON(칸 없음)도 읽힌다(시험).
- 레이팅 규칙은 `GameProfile`: `chart_rating`, `rating_divisor`(CHUNITHM 50·maimai 1), `overall_places`(4·0), `displayed_places`(2·0), 램프 우열표 3개, `candidate_target_score`. maimai 곡 레이팅은 `services/maimai/rating.py`(maimai.py `utils/coefficient.py`의 계수표, 달성률 100.5% 상한, 정수 버림). 후보곡 상승폭은 CHUNITHM의 "상수+2.00" 대신 기준 점수의 곡 레이팅을 프로필 함수로 구한다(CHUNITHM은 같은 값).
- 램프 칸: maimai 콤보(FC·AP)는 `combo_lamp`, 싱크(FS·FDX)는 `chain_lamp`, `clear_lamp`는 빈 값. 문자열 이름은 프로필 순서표가 정하고 어댑터가 맞춰 넘긴다.
- 상태 태그 `maimai-synced`를 `STATUS_ONLY_TAGS`에 더했다. 태그 설명(`defines_tags`)은 Part 6.

남은 것: `fetch_for_sync`(maimai) 자체와 파서(Part 3), 계산 레이팅과 NET 표시 레이팅 대조(§17.9 2번), 표시(달성률 `100.5000%` 등)는 Part 6. 스킬(`goals`의 `chart_rating`, `updates`의 `candidate_upside`)은 아직 CHUNITHM 직결이다(Part 6).

### 17.9 정할 것

1. **유니 인격과 maimai**: 유니는 츄니즘 캐릭터다(`00-core.md` "여러 게임"). maimai 이야기를 할 때도 같은 인격·말투로 둘지, maimai 쪽 말을 따로 둘지. Part 1~5에는 영향이 없고 Part 6 프롬프트 전에 정한다.
2. **maimai 레이팅 공식의 버전 차이**: maimai.py `coefficient`는 중국판 최신 기준이다. 국제판에서 계수·보너스가 다르면 국제판에 맞춘다 — 17.7의 NET 표시 레이팅 대조로 확인하고 그때 정한다.

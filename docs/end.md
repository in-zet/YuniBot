# 작업 마무리 체크리스트

## 1. 검증

```bash
uv sync                                    # 의존성(처음 한 번, pyproject 바뀌면 다시)
uv run pytest -q                           # 전체 시험(약 670개, 1분 안쪽)
uv run ruff check .                        # 린트
uv run basedpyright --level error          # 타입 검사 — 반드시 --level error
docker compose up -d --build               # 운영 기동(미니 PC)
```

- **`basedpyright`를 `--level error` 없이 돌리지 않는다.** 그냥 돌리면 경고 4천여 개, 약 650KB가 출력돼 그대로 컨텍스트를 채운다(2026-10-18 실측). 통과 기준은 "오류 0개"다.
- 작업 중에는 바꾼 곳의 시험만 돌린다(`uv run pytest -q skills/sync/tests` 같은 식). 전체 시험·린트·타입 검사는 작업 단위를 마칠 때 한 번 돌린다.
- 출력이 길 것 같으면 `| tail -20`처럼 끝만 본다. 실패하면 그 시험만 `-x -q`로 다시 돌린다.
- 도구 선택 평가(`uv run python3 scripts/eval_agent.py ...`)는 실제 LLM을 부르므로 키가 필요하고 비용이 든다 — 사용자가 요청할 때만 돌린다.
- 실패하면 실패한 그대로 보고한다. 스킵한 검증이 있으면 무엇을 왜 스킵했는지 명시한다.
- 디스코드에서 사람이 확인해야 할 것은 "실기 테스트로 확인할 것"으로 보고하고 `docs/plan.md` §4에 미확인으로 적는다.

## 2. 정리

- 전처리·분석용 임시 스크립트는 최종 결과물이 나왔으면 삭제한다.
- 재생성 가능한 산출물(캐시, 덤프, DB 복사본 등)은 남기지 않는다. 임시 파일은 애초에 `temp/`(git 제외)에만 만든다.
- 비밀값이 코드·문서·시험에 들어가지 않았는지 확인한다(디스코드 토큰, API 키, clal 쿠키, `COOKIE_ENCRYPTION_KEY`).

## 3. progress 로그 작성

`progress/YYYY-MM-DD.md`(오늘 날짜, 없으면 생성)에 추가한다.

```
- ~~무엇~~ 구현/생성/수정/삭제
```

**항목당 1~2줄.** 상세 설명은 로그에 쓰지 말고 해당 문서로 옮긴 뒤 포인터만 남긴다.
**기각한 접근과 그 이유는 반드시 적는다** — 다음 세션이 같은 걸 다시 시도하는 것을 막는 유일한 장치다.
미정 항목과 **다음 시작점**도 이 파일 맨 아래에 적는다.

## 4. 문서 갱신 확인

`docs/doc-guide.md`의 라우팅 표에 따라 이번 세션 내용을 각 문서로 보냈는지 확인한다.

| 변경 종류 | 확인할 문서 |
|---|---|
| 단계 완료 · 범위 변경 · 새 리스크 발견 | `docs/plan.md` |
| 설계서와 다르게 구현한 것(합의된 것) | 해당 `docs/design/` 파일 |
| 폴더/파일 구조 변경 | `docs/INDEX.md` (+ `docs/conventions.md` §1) |
| 스택·하드 제약·레드라인 변경 | `CLAUDE.md` |
| 검증 절차 변경 | 이 문서 §1 |

## 5. 커밋과 대기

- 검증(§1)까지 마친 작업 단위는 승인 없이 바로 커밋한다(이번 작업 단위의 변경만 묶는다). 여러 작업 단위를 묶은 큰 작업이 끝나면 승인 없이 바로 `git push`한다(2026-10-18 결정).
- 작업 단위 완료 후 사용자 명령을 대기한다.

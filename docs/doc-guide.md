# 문서 관리 지침

문서를 쓰기 전에 **"이 내용이 이 문서의 역할에 맞는가"** 를 먼저 판단한다. 맞지 않으면 문장을 고치지 말고
아래 라우팅 표에 따라 옳은 문서로 옮긴다.

## 1. 문서별 역할

| 문서 | 역할 (한 줄) |
|---|---|
| `CLAUDE.md` | 세션마다 자동 로드되는 최소 규칙 + 다른 문서로 가는 포인터 |
| `docs/INDEX.md` | 어떤 파일이 어디 있고 어떤 상태인지의 경로 색인 |
| `docs/doc-guide.md` | 이 문서 — 무엇을 어디에 쓸지의 규칙 |
| `docs/start.md` / `docs/end.md` | 세션 시작·종료 시 밟을 절차 |
| `docs/plan.md` | 범위 · 작업 단계 · 결정 기록 · 리스크 |
| `docs/conventions.md` | 개발 규칙(폴더·third_party·DB·시험·주석) |
| `docs/pitfalls.md` | 실제로 겪은 함정 모음 |
| `docs/design/00-core.md` | 코어 설계서 — 구조, 스킬 규격, 서비스, 이벤트, 권한, 인격, 운영 |
| `docs/design/skills/<스킬>.md` | 스킬 설계서 — 동작, 도구, 이벤트, 데이터, 설정, 지침, 시험, 구현 결정 |
| `progress/YYYY-MM-DD.md` | 날짜별 작업 로그 + 미정 항목/다음 시작점 |

문서가 늘어나면 이 표와 `docs/INDEX.md`에 같이 등록한다.

## 2. 라우팅 — 이런 내용은 이 문서로

| 쓰려는 내용 | 목적지 |
|---|---|
| 범위, 작업 단계, 여러 스킬에 걸친 결정, 리스크 | `plan.md` |
| 스킬 하나의 동작·도구·데이터, 그 스킬에서 정한 세부 | 그 스킬의 `docs/design/skills/<스킬>.md` |
| 코어·서비스·이벤트·권한 규격 | `docs/design/00-core.md` |
| 구조·DB·시험·주석 규칙 | `conventions.md` |
| 어느 폴더에 어떤 파일이 있는가 | `INDEX.md` |
| 스택·하드 제약·레드라인 | `CLAUDE.md` (규칙 한 줄 + 포인터만) |
| "이렇게 썼더니 이렇게 동작하더라" (실패 경험) | `pitfalls.md` |
| 오늘 무엇을 했는가, 아직 정해지지 않은 것, 다음에 할 것 | `progress/` |

**계획 파일은 만들지 않는다.** 작업 계획은 채팅으로 짧게 말하고, 남길 결정만 위 표의 문서로 보낸다.

## 3. 문서별 금지 사항

- **`CLAUDE.md`**: 사례·설명·근거 금지. 규칙 한 줄과 포인터만
- **`progress/`**: 서술형 일기 금지. 항목당 1~2줄, 상세는 다른 문서로 옮기고 포인터만
- **`INDEX.md`**: 기능 설명 금지. 경로·한 줄 설명·상태만
- **설계서**: 코드를 통째로 옮겨 적지 않는다. 동작과 규칙만 적고, 코드는 파일 경로로 가리킨다

## 4. 폐기된 안의 처리

기획 단계에서 버린 안은 문서에서 **완전히 삭제**한다. 대안을 비교한 흔적도 남기지 않는다.
그런 이력이 필요하면 그날짜 `progress/`에만 남는다. 단 **실제로 해 보고 실패한 것은 남긴다** —
같은 함정을 다시 밟지 않기 위한 것이므로 폐기 이력과 성격이 다르다.
"다시 제안하지 말 것"은 `plan.md` §1 "제외"에 한 줄로 둔다.

## 5. 비대화 방지 기준

넘으면 분할이나 이관을 검토한다. 절대 규칙이 아니라 점검 신호다.

| 문서 | 기준 |
|---|---|
| `CLAUDE.md` | 100줄 |
| `INDEX.md` 표의 셀 하나 | 3줄 |
| `progress/` 항목 하나 | 2줄 |
| 스킬 설계서 하나 | 15KB |

## 6. 문서 수정 전 확인

기존 문장을 고치기 전에, 그 문단이 지금 문서의 역할에 맞는지부터 본다. 맞지 않는 문단을 다듬는 것은
비대화를 늦출 뿐 방향을 되돌리지 못한다.

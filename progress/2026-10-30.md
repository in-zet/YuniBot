# 2026-10-30

## 17단계 Part 3: aime 인증 공통화와 maimai DX NET 어댑터
- SEGA 사이트 복구 뒤 실측. 처음엔 `maimaidx-eng.com`이 80/443 모두 연결 거부라(CHUNITHM 사이트는 정상) 멈추고 보고했고, 사용자가 복귀를 알려 준 뒤 이어서 했다. 점검 시간대가 아니었으니 사이트 쪽 문제였다.
- 쿠키: 실행 중 컨테이너의 DB가 옛 스키마(`chunithm_net_cookies`, 마이그레이션 022~028 적용 전)라 실측 스크립트는 읽기 전용으로 옛 테이블에서 읽었다. 스크립트·원본 HTML·pickle은 모두 세션 임시 폴더에만 두고 지웠다. 저장소에는 개인 정보를 지운 표본만(`docs/reference/maimai-net/`).
- **베스트 목록 페이지가 있다**(사용자 추정이 맞았다): `home/ratingTargetMusic/`. 그런데 "Songs for Rating(New/Others)" 뒤에 비어 있는 "Songs for Rating Selection(New/Others)" 머리글이 더 있어, 처음 정규식(`\((New|Others)\)`)은 그 뒤 항목까지 구곡으로 끌어와 35가 아니라 54가 나왔다. 머리글을 `fullmatch`로 정확히 읽는다.
- **레이팅 대조(§17.9 2번 확정)**: NET이 준 신곡 8 + 구곡 35 목록과 곡 DB 상수로 계산한 합이 프로필 레이팅과 같았다(8564). 목록을 안 주고 전체 기록에서 프레임을 직접 짜도 같았다. `RecordsService.save_sync`에 실제 스냅샷을 넣어 `rating_mismatch=False`까지 확인했다(메모리 DB).
- **신곡 판정 버그**(Part 4에서 만든 것): 곡 DB 최신은 CiRCLE PLUS(265)인데 NET 신곡 15곡은 CiRCLE(260) 곡이었다. 곡 DB 쪽 `intl=1`은 PLUS 곡을 이미 담고 있다(`date_intl_added` 2026-10-16). maimai DX 이후는 PLUS를 같은 세대(앞 두 자리)로 묶는다. NET 목록이 `best`/`new`로 오는 동안은 레이팅에 영향이 없지만 신곡 필터·후보곡·프레임 직접 짜기에 영향이 있었다. 이전엔 이 버전 판정을 곡 DB 안에서만 시험해 놓쳤다.
- 오류 코드: 로그인이 풀리면 `/maimai-mobile/error/`로 가는데 코드가 100001만이 아니었다(200002도 봤다). CHUNITHM-NET과 같은 세 코드(100001·200002·200004)를 로그인 풀림으로 본다. 처음에 100001만 풀림으로 본 탓에 첫 실호출이 "오류 코드 200002로 막았어"로 끝났다.
- 파서는 maimai.py를 읽지 않고 페이지 구조를 직접 읽어 새로 썼다. 목록 항목의 오른쪽 그림 3개는 HTML 순서로 싱크·콤보·랭크(`float:right`라 화면에서는 뒤집혀 보인다). 宴은 난이도 클래스가 `music__score_back`(이름이 빈 칸)이고 친 적 없는 곡 89개가 전부 STD 그림이었다.
- 램프 그림은 이 계정에 FC/AP/싱크 기록이 없어 실제 최근 플레이 쪽 그림 이름을 못 봤다. 목록 요약 표의 `music_icon_*` 이름을 기준으로 하고 `…plus`·`fsd` 철자도 같이 받는다 → 실기 확인 대상(§17.10).
- 중복 제거: 쿠키 복호화·만료 처리가 CHUNITHM 서비스에만 있어 `SegaCookieStore`로 뽑아 두 서비스가 쓴다(기존 시험 그대로 통과).
- 시험 함정: 이 세션에서 만든 일회용 스크립트가 예외로 끝나면 `aiosqlite` 연결이 안 닫혀 프로세스가 영영 안 끝난다(`| tail`이라 출력도 안 보임). `-u`와 `faulthandler.dump_traceback_later`로 잡았다.
- 다음 시작점: Part 6-5b(`sync`·`report`·`goals`·`session`을 maimai로) — `sync`는 아직 `games: [chunithm]`이라 maimai 동기화를 부를 길이 없다. 서비스는 준비됐다(`ctx.chunithm_net.fetch_snapshot`).

## 17단계 Part 6-5b: sync·report·session·goals의 maimai 대응
- **가장 큰 함정: 이벤트 핸들러의 ctx는 기본 게임(CHUNITHM) 서비스를 들고 있다.** `maimai.sync.completed`를 받는 report/goals 핸들러가 `ctx.records`를 부르면 CHUNITHM 기록을 읽는다(시험의 가짜 서비스로는 안 잡힌다). 도구 실행기만 `ctx.game`에 맞춰 서비스를 바꾸고 이벤트 버스는 안 바꿨기 때문이다. 해결: `ToolContext.game_services` + `for_game()`을 만들고 실행기·버스가 같이 쓰게 했다. 낸 쪽의 게임은 `ctx.emit*`가 버스에 넘긴다. 예약 이벤트(`goals.notify_due`)에는 게임이 없어 목표의 `game`으로 다시 바꾼다(시험: 기본 게임 ctx로 maimai 목표의 예약 알림을 만들어 maimai 기록으로 계산되는지).
- `@on`은 함수당 이벤트 하나만 달 수 있다(속성을 덮어쓴다). 게임 둘을 받는 핸들러는 얇은 함수 둘이 본체 하나를 부른다(`notes`가 먼저 이렇게 했다).
- report/goals/session의 CHUNITHM 출력은 글자까지 그대로 두려고 했다(기존 시험 전부 통과). 달라진 것: 프로필·동기화 리포트의 `레이팅`·`베스트 30`·`신곡 20` 줄 앞 라벨의 띄어쓰기(`ljust(8)`), 그리고 도움말의 "더 쓰고 싶다면" 한 줄(maimai-synced 정의가 생겨서).
- goals 설계 결정(2026-10-30, 사전 승인 범위 안): 폴더의 `cleared` 조건은 maimai에서 거절(클리어 램프 없음), 오버파워는 거절. 곡 목표의 "안 쳐 본 채보" 기준점 여백(15,000)은 maimai에서는 달성률 1.5%p로 같은 숫자를 쓴다(점수가 ×10000이라). 이 값이 maimai에 맞는지는 실기에서 본다.
- 후보곡의 "남은 점수"는 달성률 게임에서는 노트 가중치에 달려 있어 칸을 두지 않았다(CHUNITHM의 `remaining_to_target`은 1,010,000점 척도라 그대로 쓰면 틀린 값이 나온다).
- 안 한 것: `arcade`·`settings`·`updates`, 목표 알림의 게임 이름 표기. 시험은 진짜 `RecordsService`·`MaimaiSongDbService`로 동기화한 기록 위에서 한다(`skills/*/tests/test_maimai_*.py`).
